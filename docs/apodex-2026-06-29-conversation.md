# 燎客 AI · 消费返现 + 店长返利：两道关卡都能过的完整闭环设计

## 这套模式能跑通，但顺序不能乱

技术上，"消费返现 + 老带新秒返利"完全可以实现：微信支付分账接口支持交易完成后实时分账 [1]，有赞等平台已有自动返现到余额的成熟案例 [2]。商业逻辑上也成立——余额锁定复购、分享驱动拉新、数据沉淀锁定商家。

但这套系统有两道关卡必须按顺序过：**先合规，再算账，最后才是产品设计**。顺序乱了，合规问题会在系统上线后变成刑事风险，财务问题会在商家第一个月后导致停用。

本报告按这个顺序推导：合规边界 → 经济模型 → 产品设计 → 自动化机制 → 复制扩张 → 健康监控。

---

## 合规边界：把"店长返利"设计成一级分销而不是传销

### 法律判定传销的三要件

《禁止传销条例》明确传销的认定需同时满足三个要件：**缴纳入门费**（以购买商品或缴费作为加入条件）、**拉人头计酬**（按发展下线人数给予奖励）、**团队计酬**（按下线及下下线的销售业绩给予奖励）[3]。刑事追诉的门槛是参与人员 30 人以上、层级 3 级以上 [4][5]。

一级分销只要基于真实交易、无入门费，不满足上述要件，属于合法的推荐奖励 [3]。超过三级则在司法实践中容易被认定为传销 [6]。

### 合规 vs 违规的结构差异

| 设计维度 | 合规设计（燎客应采用） | 违规设计（必须避开） |
|---------|-------------------|------------------|
| 层级结构 | 仅一级：A 带来 B 消费，A 得返利；B 再带来 C，A **不得**返利 | 二级及以上：A 对 B 带来的 C 的消费也有分成 |
| 触发条件 | 新客**真实到店消费核销**后触发 | 新客注册、扫码、或充值即触发 |
| 入门要求 | 进入小程序即成"店长"，零入门费、零门槛 | 要求先消费或付费才能获得推荐资格 |
| 系统话术 | "分享奖励""推荐有礼""带朋友来吃" [7] | "上下线""下线业绩""团队计酬""层级收益" |
| 奖励上限 | 设置每月每人返利上限，避免无上限被认定违规 | 无上限、无约束 |

微信小程序运营规范明确禁止以高返利为噱头的诱导欺诈行为 [8]，因此话术层面同样需要约束。

### 燎客系统必须锁死的三条架构约束

**约束一：推荐关系只记录一跳。** 数据库中推荐关系表只存储"直接推荐人 ID"，不存储间接层级。当 B 带来 C 消费时，系统查推荐关系只找 B 的直接推荐人（即 C 的返利接收方是 B，不是 A）。

**约束二：返利触发事件是"核销完成"，不是"注册"或"扫码"。** 消费核销接口返回成功后，系统才异步调用分账接口。注册事件、扫码事件均不触发任何资金流动。

**约束三：前端和通知文案中禁止出现层级相关词汇。** 统一使用"分享奖励""推荐有礼"等表述 [7]，燎小星的话术模板库中过滤掉所有传销敏感词。

## 经济模型：算清楚商家能给多少

### 基准数据与利润空间

以牛里牛气为基准：16 张桌、人均 50 元、日均 40 人，月营收约 6 万元。

餐饮行业净利润率参考区间：KPMG 2025 年餐饮行业报告显示行业面临成本压力 [9]；百胜中国 Q3 2025 净利率约 17.3%，是连锁头部的上限 [10]。中小独立餐饮的净利率通常在 8%–12% 区间，毛利率（扣除食材成本后）在 55%–70% 区间。

**关键财务逻辑：** 返现余额不可提现这一设计，把"名义成本"和"实际现金成本"拉开了差距。假设返现使用率为 60%（即发出去的余额有 40% 过期沉淀），名义 8% 返现比例的实际现金支出只有约 4.8%。这是这套设计最重要的财务优势——对商家现金流的冲击远小于直接发现金。

### 三档参数对比（示意性测算）

以下为基于牛里牛气基础数据的示意性测算。输入假设：月营收 6 万元，扫码率 40%（480 人/月进入私域），老带新转化率 20%（即 480 人中 96 人分享，每人平均带来 0.25 个新客 = 24 新客/月），新客人均消费 50 元。

| 参数档位 | 消费返现比例 | 老带新返利 | 系统服务费 | 名义总成本率 | 实际现金成本率（60%使用率）| 月净利影响（在 10% 净利率基础上）|
|--------|-----------|---------|---------|-----------|----------------------|--------------------------|
| **保守档** | 5% | 5 元/单 | 699 元/月 | 约 7.4% | 约 4.6% | 净利率约 5.4%，可接受 |
| **标准档** | 8% | 10 元/单 | 699 元/月 | 约 10.6% | 约 6.6% | 净利率约 3.4%，需用增量营收覆盖 |
| **激进档** | 12% | 15 元/单 | 699 元/月 | 约 14.8% | 约 9.6% | 净利率约 0.4%，仅靠增量单量支撑 |

> **示意性测算说明**：以上数字基于牛里牛气基础数据和假设的扫码率、转化率推导，实际结果随门店客流、使用率、新客转化率波动较大。"实际现金成本率"假设 60% 余额被核销使用，其余 40% 过期沉淀。

**推荐采用标准档**，理由：5% 返现对用户感知偏弱（50 元消费只返 2.5 元，用户不会为此改变行为）；8% 返现（50 元消费返 4 元）加上 10 元老带新返利，用户能感知到真实好处，分享动机明显强于保守档。增量营收（老带新 24 单 × 50 元 = 1,200 元 + 复购提升估算）在多数情况下可以覆盖净利率压缩。

**财务安全阀：** 系统服务费 699 元/月占月营收约 1.2%，商家在净利率 10% 的基础上仍有空间。若商家净利率低于 8%，建议先用保守档验证效果，再逐步上调。

## 产品设计：用户端与商家端的完整闭环

### 完整数据流链路

```
顾客扫桌牌二维码
 └─ 系统检测来源链接是否携带推荐码
 ├─ 有推荐码 → 绑定推荐关系（有效期：首次消费前 30 天内，超时失效）[11]
 └─ 无推荐码 → 直接进入
 └─ 燎小星接待 → 引导领券 → 进入会员体系

顾客消费 → 店员核销
 └─ 核销接口返回成功
 ├─ 系统计算返现金额（消费金额 × 返现比例）
 ├─ T+0 写入顾客"燎客余额"账户（账户类型：store_credit，不开放提现接口）
 └─ 检测是否存在上级推荐人
 ├─ 有推荐人 → 调用微信支付分账接口 → 秒返利到推荐人余额 [1][12]
 └─ 无推荐人 → 流程结束
 └─ 燎小星推送通知："你的返现已到账，下次来用"

推荐人余额到账
 └─ 燎小星推送："恭喜！你带来的朋友刚刚消费，X 元已到账"
 └─ 推荐人余额累计 → 激励下次到店使用
```

### 用户端新增模块

**1. 燎客余额账户（整合两类余额）**

将"消费返现余额"和"老带新返利余额"合并为一个"燎客余额"账户，展示在用户首页"我的钱包"区域。

- **余额来源**：消费返现（每次核销后 T+0 自动入账）、推荐返利（新客首次核销后秒到账）
- **余额使用**：结账时出示余额抵扣码，店员扫码核销，单次抵扣上限建议为本单消费金额的 30%（与微信支付分账上限对齐 [13]）
- **不可提现实现**：后端账户类型字段标记为 `store_credit`，不开放提现接口，前端隐藏"提现"入口，用户协议中明确标注为"消费奖励，仅限本店消费抵扣"
- **有效期**：建议 180 天滚动有效期（每次新增余额重置计时），过期前 7 天触发提醒
- **展示字段**：累计获得 / 已使用 / 当前可用 / 即将过期（最近 14 天内到期金额）
- **明细记录**：每笔来源（消费返现 / 推荐返利）+ 金额 + 时间 + 对应订单

**合规说明**：余额来源为消费后赠送的奖励，而非用户主动充值的预存资金，因此不属于《单用途商业预付卡管理办法》规制的预收资金范畴 [14]，可规避备案和资金存管要求。

**2. 店长身份与分享入口**

- **自动激活**：用户首次进入小程序即获得"店长"身份，无需申请、无需付费、无入门条件
- **分享入口**：首页固定展示"我的专属海报"按钮，一键生成带推荐码的 AI 海报或短链
- **推荐码绑定逻辑**：新用户通过老用户海报/链接进入 → 系统记录推荐关系（有效期 30 天）[11] → 新用户首次消费核销 → 触发返利到推荐人余额
- **层级锁死**：数据库推荐关系表只存储一跳（`referrer_id` 字段），B 带来 C 消费时，返利接收方只查 C 的直接推荐人 B，不向上追溯 A

### 商家端新增模块（接入现有商家版 PRD）

**1. 返现策略配置**（挂载在现有"活动"Tab 下）

| 配置字段 | 类型 | 说明 |
|--------|-----|-----|
| `cashback_rate` | float | 返现比例（%），建议范围 3%–15% |
| `cashback_scope` | enum | 全单 / 指定品类 |
| `effective_time` | datetime range | 生效时间段 |
| `is_active` | bool | 开关，可随时暂停/恢复 |
| `monthly_cost_alert` | float | 成本预警阈值，超过时系统提醒 |

商家端自动计算"本月预计返现总额"：`本月已核销金额 × cashback_rate`，超过阈值时在首页展示黄色警告卡片。

**2. 老带新返利配置**

| 配置字段 | 类型 | 说明 |
|--------|-----|-----|
| `referral_reward` | float | 每单返利金额（元） |
| `monthly_cap_per_user` | int | 每人每月最多获得返利次数上限 |
| `new_customer_reward` | float | 新客首单优惠券面值（元） |

返利发放记录需展示：谁带来了谁、何时消费、返了多少、是否已到账。

**3. 余额核销入口**（接入现有"核销"模块）

在现有核销页新增"余额抵扣核销"方式：顾客出示余额抵扣码 → 店员扫码 → 系统显示可用余额和本单抵扣上限 → 确认抵扣金额 → 写入核销记录。核销记录需关联到对应会员账户，支持对账查询。

## 自动化运行机制：让系统不需要人盯

### 自动化触发链路

| 触发条件 | 系统自动动作 | 用户感知 |
|--------|-----------|--------|
| 顾客通过推荐链接进入小程序 | 检测 URL 参数中的推荐码，写入推荐关系表，有效期 30 天 [11] | 无感知（后台静默绑定） |
| 消费核销完成（T+0） | 计算返现金额，写入顾客余额账户（`store_credit` 类型） | 燎小星推送："本次消费返现 X 元已到账" |
| 核销完成且存在推荐人 | 调用微信支付分账接口，秒返利到推荐人余额 [1] | 推荐人收到："你的朋友刚刚消费，X 元奖励已到账" |
| 余额距到期剩余 7 天 | 燎小星发送提醒通知 | "你有 X 元余额将在 7 天后过期，快来用" |
| 顾客 30 天未到店 | 检测最近核销记录，推送召回通知 | "好久不见，你有 X 元余额等你来用" |
| 老带新成功（新客首次核销） | 推荐人余额到账 + 成长值加速 + 燎小星通知 | "恭喜带来新朋友，X 元已到账，成长值 +200" |

**技术说明**：微信支付分账 API 支持交易完成后实时分账 [1]，同一笔订单最多可发起 50 次分账请求，每次最多分给 50 个接收方 [12]。分账比例单笔累计不超过订单金额 30% [13]，这个上限覆盖了标准档"8% 返现 + 10 元返利（约 20%）"的组合。

**实施门槛需提前验证**：微信支付分账需要商家以服务商模式完成子商户入驻，入驻周期约 2–4 周 [15]。建议在牛里牛气试点启动前 4 周开始办理，避免上线时卡在支付侧。

### 商家最低介入清单

只有以下几件事需要人工操作：
1. **上线时配置一次**：返现比例、返利金额、新客优惠券面值（约 5 分钟）
2. **收银时扫码核销**：这是原有收银动作，不增加额外步骤
3. **偶尔查看首页数据**：系统每日自动汇总，老板打开看一眼即可

## 商业闭环与复制扩张

### 三方价值对照

| 视角 | 核心价值 | 留在系统里的动力 |
|-----|--------|--------------|
| **顾客** | 消费有返现（省钱）、分享有奖励（赚钱）、余额有身份感（铁杆会员更高返现比例） | 余额只能在这家店用，花不完就不想走；分享一次可能带来持续收益 |
| **商家** | 获客成本低于平台投流（平台新客获取成本通常在数十元量级，老带新成本约 10–15 元/单）；数据可见、ROI 可算 | 会员余额、推荐关系、消费记录全在燎客系统，迁移成本极高；首页数据越好看越不敢停 |
| **平台（你）** | SaaS 订阅费 + 数据网络效应 + 推荐关系图谱 | 接入门店越多，跨店数据价值越大；推荐关系网络是单个商家永远看不到的资产 |

### 低成本复制打法

**以牛里牛气为标杆**：试点跑出 4 周真实数据后，用具体数字（扫码率、老带新单数、余额核销率）去谈下一家，比任何 PPT 都有说服力。

**标准化交付包**：桌牌物料（AI 肉小签）+ 系统配置模板（返现比例 / 返利金额 / 话术）+ 3 天上线 SOP。边际交付成本主要是桌牌印刷费，系统配置约 1 小时。

**同品类优先复制**：同一品类商家互不竞争，可以共享 AI 晒圈内容模板，降低你的内容生产成本。牛里牛气跑通后，下一家火锅店可以直接复用"AI 肉小签"的物料框架，只改店名。

**商家转介绍机制**：老商家介绍新商家，给老商家一个月系统费减免。这是用你自己的"老带新"逻辑来扩张商家网络——你的获客成本等于一个月服务费，而新商家带来的是长期订阅收入。

## 系统健康监控：什么时候调整，怎么判断

### 三个核心健康指标（建议在商家版首页展示）

**指标一：余额核销率**
- 定义：本月被实际抵扣的余额 / 本月发出的返现总额
- 健康区间：40%–70%
- 低于 30% 的含义：顾客没有被"锁住"，可能是有效期太长（不紧迫）或提醒频次不够
- 触发动作：缩短有效期至 90 天，增加"余额即将过期"提醒频次

**指标二：老带新转化率**
- 定义：生成分享海报的用户中，真正带来新客首次核销的比例
- 健康区间：15%–25%
- 低于 10% 的含义：海报传播效果差，或新客首单门槛太高
- 触发动作：检查 AI 晒圈海报质量；考虑增加"分享即得即时小奖励"（如分享后立即得 1 元余额，不依赖新客消费）

**指标三：商家月度净返现成本率**
- 定义：（本月返现总额 + 返利总额）/ 本月营业额
- 健康区间：5%–12%
- 超过 12% 的含义：返现参数可能设置偏高，或老带新效果超预期导致返利支出增加
- 触发动作：超过 12% 时系统自动提醒商家检查配置；超过 18% 时平台主动联系商家，建议降低返现比例至保守档

### 阶段性扩展方向

当接入门店超过 50 家后，可以考虑两个方向：

**跨店余额**（同一品牌多店通用）：适合有多家门店的连锁品牌，进一步提升用户粘性，同时为你创造更大的数据网络价值。

**微信支付分账子商户批量入驻**：提前与微信支付服务商谈批量入驻协议，把单店 2–4 周的入驻周期压缩到标准化流程，降低每家新商家的交付时间。

系统逻辑闭环是成立的：桌边扫码捕获真实到店客 → AI 晒圈驱动内容裂变 → 消费返现锁定复购 → 老带新秒返利激励分享，这四个环节首尾相扣，商业逻辑没有漏洞。但"设计完整"和"可以落地"是两件事。当前阶段能落地的是一个精简版，而不是前面 PRD 里描述的全功能版。

**三个必须在落地前解决的卡点（按优先级排序）：**

**卡点一：微信支付分账子商户入驻（最长关键路径）**

消费返现和老带新秒返利的技术底座是微信支付分账 API，它支持交易完成后实时分账，单笔分账比例上限为订单金额的 30% [1]。但使用这个接口的前提是以服务商模式完成子商户入驻，入驻周期约 2–4 周 [2]。入驻审核本身 1–3 个工作日，但账户验证、签约、测试环境联调加在一起，实际周期拉到 2–4 周很常见 [3]。

这意味着：**今天就要启动入驻申请，不能等开发完成再办**。如果等到小程序开发完成才去办，上线日期会直接推迟 2–4 周。微信支付分账入驻是整个项目唯一不能靠加班压缩的时间节点。

**卡点二：AI 算力成本的用量上限保护机制**

在没有真实用量数据之前，算力成本是一个未知变量。如果第一批商家上线后出现异常用量（比如有用户刷量生成海报），平台方会直接亏损。必须在上线前设计好两道保护：每个用户每天最多生成 N 次 AI 晒圈（建议初期设为 3 次/天），以及每家门店每月算力消耗上限告警（超过阈值时系统推送提醒）。具体成本数字在第四节拆解。

**卡点三：合规结构必须在代码层面硬编码**

一级分销的合规边界不能靠运营人员去维护，必须在数据库结构和接口层面锁死：推荐关系表只存储直接推荐人 ID（`referrer_id`），不存储间接层级；返利触发事件绑定在核销接口的成功回调上，而非注册或扫码事件。这两条如果靠运营约束，迟早会出错 [4][5]。

### 燎客的真实差异化：三个组合拳同时存在

竞品中没有一家把以下三件事同时做到中小独立餐饮这个层级：

- **桌边扫码**：入口在每张餐桌上，100% 是已坐下点单的真实顾客，而非电梯广告或外卖包裹卡拉来的陌生人。有赞、微盟的私域入口分散在多渠道，质量参差不齐。
- **AI 晒圈**：客如云的 AI 碰碰贴（NFC）是最接近的竞品，但它是"一次性触发生成内容"，没有推荐码绑定、没有老带新返利、没有余额锁定复购。燎客是"持续运营闭环"——顾客发的每一张 AI 海报都携带推荐码，带来新客后系统自动识别并返利，客如云做不到这一点 [11][16]。
- **消费返现+老带新秒返利**：有赞有返现功能 [6][7]，但其分销层级不透明，容易滑向多级；银豹明确支持二级分销，存在传销法律风险 [15]。燎客锁死一级分销，合规边界清晰。

### 燎客的真实弱点

这些是落地阶段的真实障碍，不是系统设计问题：

- **品牌知名度为零**：商家不认识你，谈判门槛高，需要靠试点数据说话而非品牌背书。
- **没有销售团队**：早期只能靠创始人自己跑商家，获客速度慢。
- **没有客服体系**：商家遇到问题只能找你，早期运营压力全压在一个人身上。
- **技术团队规模小**：外包开发的不确定性高，上线后 bug 修复响应速度是风险点。

### 护城河的本质：数据网络效应 + 迁移成本

燎客的护城河不是技术壁垒，而是两层锁定机制叠加。

第一层是**数据沉淀锁定**：会员余额（不可提现，只能在本店消费抵扣）、推荐关系图谱（谁带来了谁）、消费记录和会员等级，全部存储在燎客系统里。商家使用 3 个月后积累数百条推荐关系和会员数据，换系统意味着这些资产全部清零——不是数据导不出去，而是导出去之后在新系统里无法还原"谁欠谁多少余额、谁的老带新关系是什么"。

第二层是**顾客习惯锁定**：顾客账户里有未用完的余额，下次来消费的概率显著高于没有余额的顾客。这部分顾客的复购行为本身就在帮商家维持客流，商家一旦停用系统，这些余额就无法继续使用，顾客体验会直接受损，商家不敢轻易停。

接入时间越长，这两层锁定越深，迁移成本越高。这是用户在和商家谈判时应该主动说出来的点，而不是等商家问。

## 四、AI 算力成本的设计与控制——利润最大的不确定变量

### 单次 AI 晒圈的成本拆解（示意性测算）

基于阿里云通义千问 Plus 和通义万相 API 的实际定价：

- **文案生成**（约 500–800 Tokens 输入 + 输出）：通义千问 Plus 输入 0.0008 元/千 Tokens，输出 0.002 元/千 Tokens [19]。按 800 Tokens 估算，约 0.002–0.004 元/次
- **图片生成**（1 张海报）：通义万相 wanx-v1 文生图 0.16 元/张 [20]
- **合计单次 AI 晒圈成本**：约 0.16–0.17 元/次（示意性测算，基于上述 API 定价）

### 单店月度算力成本推导（示意性测算）

以牛里牛气为例：月进店 1,200 人，25% 参与 AI 晒圈 = 300 次/月（注：480 人扫码 × 25% = 120 人，但每人可能多次生成，按 120–300 次区间估算）。

- 保守估算（120 次/月）：120 × 0.17 ≈ **20 元/月**
- 中等估算（200 次/月）：200 × 0.17 ≈ **34 元/月**
- 偏高估算（300 次/月）：300 × 0.17 ≈ **51 元/月**

在 699 元月费中，算力成本占比约 3%–7%，完全可控。但这个数字的前提是用量正常，一旦出现异常用量（刷量或 bug 导致循环调用），成本会线性放大。

### 三种算力成本控制方案

**方案一：按用量计费模式（推荐，适合早期）**

直接调用通义千问 + 通义万相的 API，成本随实际用量线性增长。优势是无需预付，风险是异常用量没有上限保护。**必须同时设置用量上限**：每个用户每天最多生成 3 次 AI 晒圈，每家门店每月算力消耗超过 100 元时系统告警。这两个限制在代码层面硬编码，不靠人工监控。

**方案二：包月预付模式（适合用量稳定后，通常第 3–6 个月后）**

预购 API 额度通常有折扣，适合接入 10 家以上门店、月度总用量可预测后采用。预付额度要按实际用量的 1.5 倍购买，留出缓冲。

**方案三：自建模型模式（不建议早期）**

自建模型有固定的服务器成本，只有月度 AI 调用量达到数万次以上时才比 API 调用划算。早期门店数量少，自建模型的固定成本会直接压缩毛利，不建议在接入 50 家门店之前考虑。

**健康区间判断**：算力成本占月费比例建议控制在 5% 以内（约 35 元/店/月）。超过 10%（约 70 元/店/月）时，需要检查是否有异常用量，或者考虑提高订阅价格。

## 五、平台方的成本与利润——商业模式的核心账

### 第一层：平台方的固定成本

- **小程序开发费用**：一次性，第七节详细拆解
- **服务器/云服务费**：早期（1–10 家门店）约 200–500 元/月；10–50 家约 500–1,500 元/月；50 家以上需要重新评估架构
- **微信支付服务商资质**：申请本身免费，但需要有注册公司；服务商模式下微信支付对每笔交易收取标准手续费（通常 0.6%），这部分由商家承担，不影响平台方利润
- **桌牌物料（试点期赠送）**：约 200–400 元/家，试点期的获客成本

### 第二层：平台方的变动成本

- **AI 算力成本**：约 20–50 元/月/店（示意性测算，见第四节）
- **人力成本**：早期主要是你自己的时间，建议按 100 元/小时估算机会成本
- **代运营服务成本**（如果提供托管版）：主要是策划和执行时间

### 第三层：平台方的收入结构

- **SaaS 订阅费**：699 元/月/店（成长版 Pro）
- **一次性开通费**：建议设置 500–1,000 元，覆盖桌牌物料和配置成本，避免试点期物料成本全部自己承担
- **代运营服务费**：3,000 元+/月/品牌，这是早期最重要的现金流来源
- **未来增值收入**：跨店数据分析报告、行业 benchmark 报告（需要接入 10 家以上门店才有数据支撑）

### 利润率测算（示意性测算）

| 门店数量 | 月订阅收入 | 月算力成本 | 月服务器成本 | 月人力分摊 | 月毛利 | 毛利率 |
|---------|---------|---------|-----------|---------|------|------|
| 1 家 | 699 元 | 约 35 元 | 约 300 元 | 约 500 元 | 约 -136 元 | 亏损 |
| 5 家 | 3,495 元 | 约 175 元 | 约 500 元 | 约 800 元 | 约 2,020 元 | 约 58% |
| 10 家 | 6,990 元 | 约 350 元 | 约 700 元 | 约 1,000 元 | 约 4,940 元 | 约 71% |
| 20 家 | 13,980 元 | 约 700 元 | 约 1,000 元 | 约 1,500 元 | 约 10,780 元 | 约 77% |
| 50 家 | 34,950 元 | 约 1,750 元 | 约 2,000 元 | 约 3,000 元 | 约 28,200 元 | 约 81% |

> **示意性测算说明**：人力分摊按每增加 10 家门店增加约 500 元/月估算，不含代运营服务收入。实际利润还包括一次性开通费和代运营服务费，这两项在早期可能比订阅费更重要。

**关键判断：**

- **第 1 家店必然亏损**，因为服务器和人力的固定成本无法被单店订阅费覆盖。这是正常的，不要因为第一家店亏损就动摇。
- **第 10–15 家店开始盈亏平衡**，这是纯靠订阅费的平衡点（不含代运营）。
- **第 50 家店毛利率超过 80%**，规模效应显现，服务器和算力成本边际递减。

**代运营服务是早期最重要的现金流来源**。在接入前 10 家门店期间，代运营服务费（3,000 元+/月/品牌）的重要性远高于订阅费。建议前 3 家试点商家提供免费代运营，用真实数据和效果换口碑；第 4 家起开始收代运营费。

**全职时机判断**：建议接入 20 家门店、月收入（订阅+代运营）稳定超过 15,000 元后考虑全职。在此之前，保持副业状态可以降低个人财务风险，同时用真实数据验证模型。

## 六、迭代升级路线图——先跑通闭环，再加功能

**核心原则**：第一个月不要堆功能，先把核心闭环（桌边扫码 + AI 晒圈 + 消费返现 + 老带新）跑通，用真实数据告诉你哪里需要迭代。如果某个指标连续 2 周低于健康区间，就是迭代信号。

### 迭代路线图

| 月份 | 功能方向 | 目标指标 | 受益方 | 优先级 |
|-----|---------|---------|------|------|
| 第 1 个月 | 核心闭环上线（扫码+AI晒圈+返现+老带新） | 扫码率 > 30%，老带新 > 10 单/月 | 商家+顾客 | 🔴 必须 |
| 第 2 个月 | 余额到期提醒优化（到期前 7/3/1 天分别提醒） | 余额核销率从 60% 提升至 70%+ | 顾客 | 🔴 高 |
| 第 2–3 个月 | 数据报表升级（经营洞察：高价值顾客画像、老带新时段分析） | 商家续费率 > 80% | 商家 | 🔴 高 |
| 第 3 个月 | 会员等级可视化（成长值进度条 + 升级奖励） | 铁杆会员（Lv3）占比 > 10% | 顾客 | 🟡 中 |
| 第 3–4 个月 | AI 内容模板库（节日/品类预设模板，商家一键启用） | AI 晒圈参与率从 25% 提升至 35% | 商家+顾客 | 🟡 中 |
| 第 4–6 个月 | AI 晒圈内容升级（动态海报、短视频模板） | 发圈率提升 10%+ | 顾客 | 🟡 中 |
| 第 6 个月后 | 跨店数据 benchmark（需 10+ 家门店）| 商家认知平台价值 → 降低流失率 | 商家 | 🟡 中 |
| 第 6 个月后 | 多门店管理（连锁品牌统一后台） | 单客户月费从 699 元升至 1,500+ 元 | 商家 | 🟡 中 |
| 第 9–12 个月 | 跨店通用余额（同城多店接入后） | 平台整体余额核销率提升 | 顾客 | 🟢 低（需规模支撑） |

**增加商家粘性的核心逻辑**：数据报表升级（第 2–3 个月）和跨店 benchmark（第 6 个月后）是最关键的两步。前者让商家每天打开后台有"收获感"，后者让商家意识到"这个数据只有平台能提供"，形成不可替代性。

**增加顾客粘性的核心逻辑**：余额到期提醒（第 2 个月）的 ROI 最高——改动量小，但直接拉升余额核销率，核销率越高，顾客复购越多，商家续费意愿越强，这是一个正向循环。

## 七、和商家怎么谈——谈判策略与话术设计

谈判的核心目标只有一个：**让商家自己算出 ROI，而不是你告诉他这个系统好**。你的工作是提供数字和框架，让他做算术。

### 阶段一：破冰（前 5 分钟）

不要先介绍系统。开口第一句话问商家的痛点：

> "你现在每个月在美团/抖音上大概花多少投流费？"

让他说出数字。他说完之后，你说：

> "我做的这套东西，就是帮你把这笔钱省下来，让顾客帮你带顾客。"

这一句话定位了你的价值，也让他感觉你在解决他的真实问题，而不是在卖软件。

### 阶段二：演示（10–15 分钟）

用牛里牛气的数据做案例（有试点数据更好）。重点不是讲功能，而是让他**亲身体验顾客视角**：

> "你扫一下这个桌牌，我给你演示顾客看到的是什么。"

让他自己扫码，看到燎小星欢迎、领券、AI 晒圈的完整流程。亲身体验的说服力远高于 PPT。

### 阶段三：算账（5–10 分钟）

拿出第三节的财务模型，用他自己的数据算：

> "你这家店每天大概多少人？人均消费多少？我们按最保守的情况算，一个月大概多出来多少单，多赚多少钱。"

强调：**第一个月免费试点，你零风险**。先看数据，再决定要不要继续付费。

### 阶段四：处理反对意见

以下是最常见的 5 个反对意见和标准回应话术，可以直接背诵：

**"顾客不会扫码的"**
> "桌牌上写的是'扫一下有券，AI 帮你做朋友圈大片'，好奇心驱动，不需要教育顾客。你现在点菜的时候有多少人会扫码点餐？同样的道理。"

**"我没人管群"**
> "不需要你管群。系统自动运营——新客进来自动发欢迎语和券，7 天没来自动发召回券，生日自动发礼品券。你只需要员工说一句话：'扫码有券，还能 AI 出大片。'"

**"顾客数据安全吗，是你的还是我的？"**
> "群主是你，好友在你手机里，会员数据在你后台，随时可以导出。我只提供工具，不碰你的顾客，也不会把你的顾客推给别的店。"

**"699 元太贵了"**
> "先免费试一个月，看数据再决定。如果一个月后老带新不超过 10 单，你不用付一分钱。如果超过了，699 元你觉得贵吗？"

**"我担心这个不合法，是不是传销？"**
> "不是。这套设计只有一级——你的老顾客带朋友来，老顾客得奖励，新顾客得优惠。新顾客再带他的朋友来，是新顾客得奖励，不是老顾客再得一次。没有层级，没有入门费，完全合法 [4][5]。"

## 八、和开发团队怎么谈——外包开发的关键控制点

### 维度一：功能范围的界定（最重要）

必须在合同中明确"第一版 MVP 包含哪些功能、不包含哪些功能"。外包开发最常见的失控原因是功能范围不清晰，导致开发方不断要求加钱或延期。

**MVP 必须包含的功能**：

- 用户端：桌边扫码进入 → 燎小星欢迎 → 领券 → AI 图文生成（调用通义千问+万相 API）→ 海报生成与分享 → 推荐码绑定（后端实现）
- 商家端：首页数据概览（今日扫码/领券/老带新数）→ 会员列表（基础筛选）→ 核销（扫码+手动输入）→ 基础活动配置（老带新奖励开关）
- 后台：推荐关系记录（一跳，不存间接层级）→ 余额账户（store_credit 类型，不开提现接口）→ 消费返现计算 → AI 用量统计（按门店查看）

**明确排除在 MVP 之外的功能**：复杂会员等级（成长值进度条）、跨店余额、视频海报、代运营后台、多门店统一管理。这些排除条款必须白纸黑字写进合同，防止开发方"顺手做了"然后要求追加费用。

### 维度二：技术架构的关键要求

必须向开发团队明确以下四条技术要求，并在验收标准中体现：

1. **微信支付分账接口必须用服务商模式**，不能用普通商户模式。普通商户模式无法实现实时分账 [1]。
2. **推荐码绑定逻辑必须在后端实现**，不能只在前端做。前端绑定可以被绕过，后端绑定才能保证数据准确性。
3. **余额账户必须有完整的流水记录**，每笔入账（来源：消费返现/推荐返利）和出账（核销抵扣）都要记录，支持商家端对账查询。
4. **所有 AI 调用必须有用量统计**，支持按门店、按用户、按时间段查看，这是控制算力成本的基础。

### 维度三：合同条款的关键点

- **代码所有权归你**，不是开发方。这一条必须明确写入合同，防止开发方以"代码是我的"为由要挟。
- **分阶段付款**：30% 预付（签合同时）+ 40% 验收（核心流程跑通时）+ 30% 上线稳定运行 1 个月后。不要一次性付清。
- **验收标准是"核心流程跑通"，不是"功能做完了"**。验收时必须实际测试：扫码进入 → 领券 → AI 生成海报 → 分享 → 新用户通过海报进入并消费 → 老用户余额到账，这个完整链路跑通才算验收通过。
- **保留期**：上线后 3 个月内的 bug 修复免费，超出 3 个月按时收费。

**开发报价参考**：这个 MVP 涉及微信小程序双端（用户版+商家版）+ 后端 API + 微信支付分账集成 + 通义千问/万相 API 集成，工作量大致在 12–18 人月区间。按国内外包市场行情，综合报价通常在 15–30 万元区间（示意性参考，实际报价因团队规模、地区、技术栈差异较大）。

**关键建议：不要找最便宜的开发团队，要找做过微信支付分账的团队**。微信支付分账的服务商模式接入是整个项目技术门槛最高的部分 [2][3]，没有做过的团队会在这里踩坑，导致延期和额外成本。在筛选开发团队时，把"是否做过微信支付分账服务商模式"作为第一道筛选条件。

## 十、触发条件与决策框架——什么时候调整，什么时候加速

### 触发条件一：需要调整参数

| 观察到的信号 | 原因判断 | 具体动作 |
|-----------|---------|--------|
| 扫码率连续 2 周低于 20% | 桌牌文案吸引力不够，或摆放位置不显眼 | 换桌牌文案（测试"扫码领10元券"vs"扫码AI出大片"）；调整桌牌摆放位置至顾客视线高度 |
| 老带新转化率低于 10% | AI 海报质量差，或新客首单门槛太高 | 检查 AI 海报样式；考虑增加"分享即得 1 元余额"（不依赖新客消费就有即时奖励） |
| 商家月度净返现成本率超过 12% | 返现参数设置偏高，或老带新超预期导致返利支出增加 | 建议商家将返现比例从 8% 降至保守档 5%；同时检查是否有异常核销 |
| AI 算力成本超过月费 10% | 可能有异常用量或用量高于预期 | 查看用量统计，定位异常用户；临时降低每日用量上限 |

### 触发条件二：需要加速扩张

| 信号 | 动作 |
|-----|-----|
| 牛里牛气试点 4 周后，老带新单数超过 20 单/月 | 立刻整理成"试点数据报告"，用这个数字去谈第 2、3 家商家。真实数据的说服力远高于 PPT |
| 接入门店超过 5 家且月收入超过 5,000 元 | 考虑招募第一个兼职销售（按成功签约的门店数量给提成，降低固定成本风险） |
| 接入门店超过 10 家 | 开始收集跨店数据，为 benchmark 报告做准备；同时考虑提高一次性开通费至 1,000 元 |

### 触发条件三：需要暂停或重新评估

**商家转介绍机制**：当接入 20 家门店后，可以设计一套"老商家带新商家"的激励机制——老商家每成功介绍一家新商家签约，老商家当月系统费减免 50%。这是把你自己的"老带新"逻辑复制到商家获客层面，获客成本等于半个月系统费，而新商家带来的是长期订阅收入。

## 第二节：扫码行为的边界情况——并发、重复、异常场景

### 并发量级评估

以牛里牛气为例（16张桌），午晚餐高峰期极端场景：每桌2人同时扫码，峰值约32个并发扫码请求。这个量级对后端服务本身压力很小，真正的并发风险不在请求量，而在**推荐关系写入的竞争条件**——两个用户同时通过不同海报进入，系统可能同时尝试给同一个新用户绑定不同的推荐人。

微信支付分账接口的单个服务商QPS限制为300 [7]，远高于餐饮门店核销峰值（16桌同时核销约32次/小时），并发侧不构成瓶颈。微信小程序扫码跳转通过URL参数传递业务数据（store_id、table_id、referrer_id），不同用户扫同一桌牌会得到相同的URL参数，系统通过`openid`区分不同用户 [8]。

### 扫码场景完整响应逻辑

| 扫码场景 | 系统响应逻辑 | 技术实现要点 |
|---------|-----------|-----------|
| **正常首次扫码（无推荐码）** | 创建会话，燎小星弹出欢迎语，引导领券 | 写入session记录，标记entry_source=direct |
| **通过海报扫码（有referrer_id）** | 检查推荐关系是否已存在；若无则写入（首次绑定优先）；燎小星欢迎 | 数据库加唯一约束`UNIQUE(referred_id, store_id)`，SETNX分布式锁防并发写入 |
| **同一用户同一餐次重复扫码** | 检测到同一openid已有活跃会话；不重新发券；燎小星显示"欢迎回来" | 领券接口幂等校验：同一openid+store_id+当日，券已存在则返回已有券ID |
| **同一桌不同顾客先后扫码** | 各自独立会话，各自领各自的券 | table_id仅用于统计，不影响用户维度的幂等控制 |
| **扫码后关闭小程序不领券** | 推荐关系已写入（如有referrer_id），等待30天内首次消费触发返利 | 推荐关系写入与领券解耦，是两个独立事件 |
| **扫码后切换小程序再回来** | 会话保持，页面状态恢复，不重新弹出欢迎语 | 通过session_id判断是否同一会话，欢迎弹窗每会话最多触发1次 |
| **截图传播桌牌，不在店的人扫码** | ⚠️ **重要漏洞**：可以领基础到店券，但AI晒圈和老带新返利不激活 | 见下方修复方案 |

### 截图传播漏洞的修复方案

**问题机制**：顾客拍下桌牌发朋友圈，朋友在家扫码，系统无法区分"真实到店"和"远程扫码"。

**修复方案**：将系统能力分为两层：

- **第一层（扫码即可用）**：领取基础到店券。这层对所有扫码用户开放，包括截图传播的用户。到店券面值低（建议不超过10元），且只有到店核销才能兑现，不到店消费无法使用，风险可控。
- **第二层（需要核销激活）**：AI晒圈生成带邀请码的海报、老带新返利计算。这两项功能的激活条件是"当日有核销记录"——即当天在本店有过一笔真实消费。未核销的用户看到AI晒圈入口，但点击后提示"先到店消费，再来晒圈赚奖励"。

**核心逻辑**：返现和返利绑定在"核销"事件上，而不是"扫码"或"领券"事件上。这是整个系统防薅羊毛的根本机制。领券只是引流钩子，资金流动只在真实消费发生后触发。

## 第三节：专属邀请码的完整设计

### 三种海报方案对比

| 方案 | 实现方式 | 用户体验 | 技术成本 | 推荐度 |
|-----|---------|---------|---------|------|
| **方案A**：每人一个带参数的专属小程序码 | 后端动态生成二维码图片，嵌入海报 | 最好，扫码自动绑定，用户无感知 | 中（每次生成海报实时调用微信API生成码） | ✅ 推荐 |
| **方案B**：海报上显示邀请码文字（如ABC123） | 静态文字，新用户手动输入 | 差，操作摩擦大，转化率低 | 低 | ❌ 不推荐 |
| **方案C**：海报上的小程序码携带referrer_id参数 | 与方案A相同，是方案A的具体实现 | 最好 | 中 | ✅ 推荐（即方案A） |

**推荐方案A的技术实现**：

用户触发AI晒圈生成海报时，后端执行以下步骤：
1. 调用通义千问API生成文案（约0.002–0.004元/次）[9]
2. 以用户的`referrer_id`（即该用户的`user_id`）为参数，调用微信小程序码生成API，生成一个携带`ref=USER_ID&store_id=STORE_ID`参数的专属小程序码图片
3. 调用通义万相API生成背景图（约0.16元/张）[10]
4. 后端合成：将文案、背景图、专属小程序码三层叠加，输出最终海报图片
5. 返回`generated_image_url`给前端展示

每次生成海报都是实时生成的个性化图片，不是静态模板。海报中的小程序码是该用户专属的，任何人扫这张海报上的码进入小程序，都会自动绑定推荐关系，用户无需任何手动操作 [11]。

### 推荐关系绑定规则：首次绑定优先

**边界情况**：用户A通过用户B的海报进入，绑定了B为推荐人；之后又通过用户C的海报再次进入，推荐关系应该绑定谁？

**结论：首次绑定优先，后续扫码不覆盖。**

理由：
- **防刷利益**：如果允许最后一次绑定覆盖，B可以找人帮自己"抢回"已经绑定给C的推荐关系，形成返利争抢。
- **用户预期**：B最先引导A进入，理应获得返利；C后来的引导不应剥夺B的权益。
- **技术实现**：数据库`referral_relation`表对`(referred_id, store_id)`加唯一约束，绑定时用INSERT IGNORE或ON CONFLICT DO NOTHING，保证只有第一次写入成功。

**有效期规则**：推荐关系绑定后30天内有效，30天内新用户首次核销触发返利；超过30天未消费则推荐关系失效，需要新用户重新通过邀请码进入才能重新绑定 [11]。首次消费核销后，推荐关系永久锁定，不再受时间限制。

**邀请码的技术参数**：邀请码即用户的`user_id`（通常为UUID或数据库自增ID），不需要单独维护一套邀请码体系。海报上的小程序码携带的是加密后的`user_id`参数，后端解密验证，防止伪造。

### 升级触发的技术链路

升级触发必须是**同步计算、异步通知**的模式：

```

 └─ 同步：检查 growth_value 是否达到下一等级阈值
 ├─ 未达到：流程结束
 └─ 达到：写入 upgrade_event（member_id, old_level, new_level, trigger_time）
 └─ 异步：推送燎小星升级通知（服务通知 + 小程序内气泡双触达）
 └─ 异步：解锁新等级权益（更新 member.level 和 level_benefits）
```

成长值计算必须和核销事务放在同一个数据库事务中，防止核销成功但成长值未写入导致不一致（漏洞M10）。

### 成长值来源与升级阈值

| 行为 | 成长值增量 | 触发条件 |
|-----|---------|---------|
| 消费 | 1元 = 1成长值 | 每次核销成功，按核销金额计算 |
| 到店核销 | +50 | 每次核销成功额外加（与消费成长值叠加） |
| 成功邀请新客首次消费 | +200 | 新客首次核销成功后，推荐人获得 |
| AI晒圈带来核销 | +300 | 通过AI海报带来的新客首次核销后，海报生成者获得 |

升级阈值：Lv1→Lv2（500成长值），Lv2→Lv3（2000成长值），Lv3→Lv4（5000成长值）。

### 各等级权益设计

中小独立餐饮净利率通常在8%–12%区间，毛利率在55%–70%区间 [12]。权益设计的约束是：折扣力度不能超过商家净利率，否则商家净亏损。以10%净利率为基准，全时段9折意味着商家让出10%毛利，净利率从10%降至约1%，处于可接受边缘。

| 等级 | 升级阈值 | 达到该等级的典型路径 | 核心权益 | 对商家的成本逻辑 |
|-----|---------|-----------------|---------|--------------|
| **Lv1 普通会员** | 注册即得 | 扫码进入 | 入群见面礼券（一次性）、生日券 | 成本约5–10元，获客成本 |
| **Lv2 熟客** | 500成长值 | 约消费400元+到店8次 | 工作日（周一至周四）95折 | 工作日填淡谷，实际成本约3%，可接受 |
| **Lv3 铁杆** | 2000成长值 | 约消费1700元+到店多次+带过新客 | 全时段9折 + 新品试吃优先报名 | 让利约10%毛利，但这类客户复购频次高，LTV高 |
| **Lv4 黑金** | 5000成长值 | 约消费4500元+大量邀请行为 | 全时段85折 + 每月赠招牌菜一份（需当月有消费） + 优先订座 | 赠菜成本约20–30元/月，但黑金客户月消费额通常在500元以上，成本占比约4%–6% |

### 降级机制：成长值不衰减，权益加活跃度门槛

**问题**：如果顾客6个月没有到店消费，成长值是否应该衰减？

- 如果降级：顾客体验极差，会直接流失，且会在社群里传播负面口碑。
- 如果不降级：高等级会员越来越多，商家成本压力持续增大。

**推荐方案**：成长值永久有效，等级只升不降。但**部分权益加活跃度门槛**：

- Lv2、Lv3的折扣权益：无活跃度要求，只要是该等级就享有。折扣是"到店才触发"的权益，不到店不产生成本。
- **Lv4黑金每月赠菜**：需要当月有至少1次消费核销记录，才能领取当月赠菜券。6个月未到店的黑金会员，等级保留，但赠菜券不发放，直到再次到店消费。

这个方案的逻辑是：折扣类权益是边际成本为零的（不到店不花钱），可以永久保留；实物类权益（赠菜）有真实成本，需要活跃度门槛控制。

## 第五节：其他没想到的漏洞——资金安全、反作弊、极端场景

### 资金安全类

**商家恶意核销（H06）**

- **问题**：商家自己用小号注册顾客账户，领券后用商家端核销，套取消费返现余额。
- **修复**：核销记录必须关联到具体员工账号（`verifier_id`字段，漏洞H12），且系统检测"同一设备openid既是核销员又是被核销顾客"的异常模式，触发人工审核告警。同时设置规则：同一openid在同一门店，单日核销金额超过阈值（如500元）时系统标记待审核。
- **优先级**：MVP必须修（基础检测规则），人工审核流程可迭代完善。

**员工私自核销（H12）**

- **问题**：店员用自己手机领券后，用商家端核销自己的账户。
- **修复**：员工账号（`role=staff`）的openid与顾客账号openid分离管理。核销接口在执行前校验：`verifier_id`对应的openid不能等于被核销顾客的openid。
- **优先级**：MVP必须修。

**余额转移套现**

- **问题**：顾客A让顾客B帮A消费，B用A的余额抵扣，A相当于把余额变现。
- **风险评估**：余额只能在本店消费抵扣，即使B帮A消费，最终也是在本店发生了真实消费，商家并未受损。这个场景对商家无害，对系统合规无影响，不需要特别限制。
- **优先级**：监控观察。

**微信支付分账失败处理（H07）**

分账接口失败的完整处理链路：

```
分账接口调用失败（超时/网络错误/余额不足）
 └─ 写入 retry_queue（order_id, retry_count=1, next_retry_time=now+5min）
 └─ 定时任务每5分钟扫描 retry_queue
 ├─ retry_count < 3：重新调用分账接口
 └─ retry_count = 3 且仍失败：写入 manual_queue，推送告警给平台运营
 └─ 运营人工处理：确认原因（子商户状态异常/分账比例超限），手动补偿
```

微信支付分账接口支持同一订单最多发起50次分账请求 [13]，重试不会产生重复分账问题，但需要在重试前查询分账结果接口确认上次是否已成功。

### 反作弊类

**刷量攻击：批量小号刷老带新返利**

- **问题**：有人批量注册微信小号，通过自己的邀请码反复"邀请自己"，每次消费都触发返利。
- **修复**：
 1. 防自我邀请：`referrer_id ≠ user_id`（漏洞H10，代码层面硬编码）
 2. 防循环邀请：A推荐B后，B不能再推荐A（漏洞H11，绑定时查推荐关系图，检测是否形成环）
 3. 设备维度限制：同一设备（微信`device_id`或小程序`unionid`）最多绑定3个不同账号；超过阈值标记为可疑账号，暂停返利发放待人工审核
 4. 消费行为异常检测：同一账号单日消费次数超过3次，或单笔消费金额与门店人均偏差超过5倍，触发人工审核

**AI生成刷量（H08）**

- **问题**：有人写脚本批量调用AI晒圈接口，消耗算力成本。基于通义千问+通义万相API定价，单次成本约0.16–0.17元 [10][9]，大量刷量会导致平台亏损。
- **修复**：
 1. 用户维度：每个`user_id`每天最多触发3次AI晒圈，超限返回"今日次数已用完"
 2. 门店维度：每个`store_id`每月AI算力消耗超过100元时，系统推送告警给平台运营
 3. IP维度：同一IP每小时最多触发10次AI生成请求
 4. 上述三个维度的计数器用Redis实现，设置TTL自动过期，不需要持久化存储
- **优先级**：MVP必须修（用量上限是控制成本的基础保障）。

**虚假核销：商家和顾客串通**

- **问题**：商家和顾客串通，虚构消费记录，套取消费返现。
- **修复**：
 1. 核销金额必须与实际收款记录关联（接入微信支付收款后可自动验证）
 2. MVP阶段暂时依赖"核销必须关联员工账号"的基础防护
 3. 后期迭代：对同一顾客在同一门店的单日核销次数和金额设置异常阈值

### 极端场景类

**商家停止使用系统后的余额处理**

- **问题**：商家不续费停用系统，顾客账户里有未用完的余额。这是法律和用户体验的双重问题。
- **修复方案**：
 1. 商家停用前30天，系统向所有有余额的顾客发送提醒："您在[店名]的余额将于X日到期，请尽快到店使用"
 2. 商家账户欠费后，顾客端余额展示保留，但标注"该门店暂停服务，余额待处理"
 3. 在用户协议中明确：余额为消费奖励，门店停业时平台协助协调但不承担兑付责任
 4. 建议商家在合同中约定：停用前需提前30天通知，并在停用前为顾客余额提供兑付期
- **优先级**：可迭代修（上线初期门店不会停用，但需在第2–3个月建立机制）。

**桌牌被竞争对手损坏或替换**

- **问题**：竞争对手故意损坏桌牌，或替换成自己的二维码。
- **修复**：
 1. 桌牌二维码携带`store_id`参数，扫码后系统验证`store_id`与当前商家匹配
 2. 建议桌牌采用防撕贴设计，或放置在商家可监控的位置
 3. 这是线下物理安全问题，系统层面只能做验证，无法完全防止
- **优先级**：监控观察。

**顾客投诉余额过期未收到提醒**

- **修复**：
 1. 余额到期前7天、3天、1天分别推送一次服务通知
 2. 通知内容明确标注：余额金额、到期日期、到店使用方式
 3. 推送记录写入数据库，顾客投诉时可查证是否已发送
- **优先级**：可迭代修（第2个月上线）。

## 第七节：完整MVP PRD文档

### 7.1 全局说明

**系统架构概述**

燎客AI系统由三端构成：
- **用户端（小程序用户版）**：顾客使用，核心路径是扫码→领券→AI晒圈→余额查看
- **商家端（小程序商家版）**：老板/店长/店员使用，核心功能是核销+数据查看+策略配置
- **后台服务（API + 定时任务）**：处理分账、成长值计算、反作弊、retry队列

**角色与权限矩阵**

| 功能 | 老板（owner） | 店长（manager） | 店员（staff） |
|-----|------------|--------------|------------|
| 查看首页数据 | ✅ | ✅ | ❌ |
| 扫码核销 | ✅ | ✅ | ✅ |
| 配置返现策略 | ✅ | ❌ | ❌ |
| 查看会员列表 | ✅ | ✅ | ❌ |
| 添加/删除员工 | ✅ | ❌ | ❌ |
| 查看老带新记录 | ✅ | ✅ | ❌ |

**核心数据流链路**

```
顾客扫桌牌二维码（携带 store_id, table_id, referrer_id）
 └─ 后端解析参数
 ├─ 有 referrer_id：检查推荐关系是否已存在
 │ ├─ 不存在：写入 referral_relation（首次绑定优先，分布式锁）
 │ └─ 已存在：忽略，不覆盖
 └─ 无 referrer_id：直接进入
 └─ 燎小星欢迎弹窗（首次进入）
 └─ 顾客领券（幂等校验）
 └─ 顾客消费 → 店员扫码核销
 └─ 核销接口成功回调（同一事务）：
 ├─ 计算返现：order_amount × cashback_rate → 写入 store_credit
 ├─ 计算成长值：order_amount + 50（到店） → 更新 member.growth_value
 ├─ 检查升级：growth_value ≥ 下一等级阈值 → 触发 upgrade_event
 └─ 检查推荐关系：是否存在有效推荐人
 └─ 存在：调用微信支付分账API（异步）
 ├─ 成功：写入推荐人 store_credit，推送燎小星通知
 └─ 失败：写入 retry_queue
```

**关键技术依赖**

- **微信支付分账（服务商模式）**：消费返现和老带新返利的资金流动底座，子商户入驻周期约2–4周 [14]，单笔分账比例上限30% [5]，单个服务商QPS限制300 [7]
- **通义千问API**：AI晒圈文案生成，成本约0.002–0.004元/次（800 Tokens） [9]
- **通义万相API**：AI晒圈图片生成，成本0.16元/张 [10]
- **Redis**：分布式锁（推荐关系绑定并发控制）、用量计数器（AI晒圈每日上限）

### 7.2 用户端PRD

#### 模块1：扫码进入与身份识别

**功能说明**

顾客扫桌牌二维码进入小程序，系统识别来源（直接进入/通过邀请码进入），绑定推荐关系。

**交互逻辑**

- **首次进入（无历史记录）**：解析URL参数 → 若有referrer_id则尝试绑定推荐关系 → 创建会员账户 → 跳转首页 → 燎小星弹出欢迎语
- **再次进入（有历史记录）**：解析URL参数 → 若有referrer_id但已有推荐关系则忽略 → 跳转首页 → 燎小星显示"欢迎回来"（仅首次进入当日会话触发一次）
- **推荐关系绑定规则**：首次绑定优先；`referrer_id ≠ user_id`（防自我邀请）；绑定前检查是否形成循环（A→B→A）；使用Redis SETNX加锁，锁粒度为`referred_id`，超时时间3秒
- **AI晒圈激活条件**：当日在本店有核销记录，才激活AI晒圈入口；否则显示"先到店消费，再来晒圈赚奖励"

**字段定义**

| 字段 | 类型 | 说明 |
|-----|-----|-----|
| `user_id` | string | 用户唯一ID（微信openid或系统UUID） |
| `store_id` | string | 门店ID |
| `table_id` | string | 桌台ID（用于统计，不影响用户维度逻辑） |
| `referrer_id` | string | 推荐人user_id（来自URL参数） |
| `entry_source` | enum | direct / referral_poster / referral_link |
| `session_id` | string | 当次会话ID（用于打扰控制） |
| `first_visit_time` | datetime | 首次进入时间 |

### 7.4 后台核心逻辑PRD（给后端开发）

#### 推荐关系绑定逻辑

**必须在后端实现，不能只在前端做。前端绑定可被绕过，合规红线。**

```
接收请求：referred_id, referrer_id, store_id

校验层：
1. referrer_id ≠ referred_id（防自我邀请，H10）
2. 查 referral_relation 表：不存在 referred_id 的已有绑定（首次绑定优先）
3. 查推荐关系图：不形成循环（referred_id 是否是 referrer_id 的推荐人，H11）

写入层（加分布式锁，key=referred_id，超时3秒）：
INSERT INTO referral_relation (referrer_id, referred_id, store_id, bind_time, expire_time, status)
VALUES (?, ?, ?, NOW, NOW+30days, 'active')
ON CONFLICT (referred_id, store_id) DO NOTHING

表结构：
referral_relation (
 referral_id STRING PRIMARY KEY,
 referrer_id STRING NOT NULL,
 referred_id STRING NOT NULL,
 store_id STRING NOT NULL,
 bind_time DATETIME NOT NULL,
 expire_time DATETIME NOT NULL,
 status ENUM('active', 'expired', 'consumed'),
 first_order_id STRING, -- 触发返利的首单ID，写入后status改为consumed
 UNIQUE KEY uk_referred_store (referred_id, store_id)
)
```

#### 消费返现计算逻辑

- **触发时机**：核销接口返回`success`后，在同一数据库事务中同步执行
- **计算**：`cashback_amount = order_amount × cashback_rate`（取门店当前配置的`cashback_rate`）
- **写入**：`store_credit`账户，`transaction_type=cashback`，`amount=cashback_amount`
- **通知**：异步推送燎小星服务通知："本次消费返现X元已到账"

#### 老带新返利逻辑

**触发时机**：新客首次核销成功后（即该`user_id`在该`store_id`的第一笔核销记录）

```
1. 查 referral_relation：referred_id=新客user_id, store_id=当前门店, status=active
2. 验证：expire_time > NOW（推荐关系未过期）
3. 验证：当前核销是该用户在本店的首次核销（查 order 表 count=1）
4. 计算分账比例验证：
 (cashback_amount + referral_reward) / order_amount ≤ 0.30
 若超过30%，取 min(referral_reward, order_amount×0.30 - cashback_amount)
5. 调用微信支付分账API [13]：
 分账接收方 = referrer_id 对应的微信支付账号
 分账金额 = referral_reward
6. 分账成功：
 - 写入 referrer 的 store_credit（transaction_type=referral_reward）
 - 更新 referral_relation.status=consumed，first_order_id=当前订单ID
 - 推荐人成长值 +200
 - 若通过AI海报带来（entry_source=referral_poster）：成长值额外 +100（合计+300）
 - 异步推送燎小星通知给推荐人："你的朋友刚刚消费，X元已到账"
7. 分账失败：
 - 写入 retry_queue（order_id, retry_count=1, next_retry_time=NOW+5min）
 - 定时任务最多重试3次，重试前先查询分账结果确认未成功
 - 3次失败后写入 manual_queue，推送告警
```

#### 成长值计算与升级触发逻辑

**成长值来源完整列表**

| 行为 | 成长值 | 触发时机 |
|-----|------|---------|
| 消费 | `order_amount`（取整） | 核销成功，同一事务 |
| 到店核销 | +50 | 核销成功，同一事务（与消费成长值叠加） |
| 老带新成功（推荐人获得） | +200 | 新客首次核销成功后 |
| AI晒圈带来核销（海报生成者） | +100（叠加在老带新+200上，合计+300） | 新客首次核销且entry_source=referral_poster |

**升级检查（每次成长值变化后执行）**

```
阈值：lv1→lv2=500, lv2→lv3=2000, lv3→lv4=5000

if growth_value >= next_level_threshold:
 old_level = current_level
 new_level = next_level
 UPDATE member SET current_level=new_level
 INSERT upgrade_event (member_id, old_level, new_level, trigger_time=NOW)
 ASYNC: 推送燎小星升级通知
 ASYNC: 解锁新等级权益
```

#### 反作弊基础规则（MVP阶段必须实现）

```
规则1：同一微信账号每天最多领取1张到店券
 实现：领券前查当日已领券记录，有则返回已有券ID（幂等）

规则2：同一user_id每日最多触发3次AI晒圈
 实现：Redis计数器，key=ai_count:{user_id}:{YYYYMMDD}，TTL=次日0点

规则3：同一IP每小时最多触发10次AI生成请求
 实现：Redis计数器，key=ai_ip_count:{ip}:{YYYYMMDDHH}，TTL=1小时

规则4：推荐关系不允许自我邀请
 实现：绑定时校验 referrer_id ≠ referred_id

规则5：推荐关系不允许循环
 实现：绑定时查询 referral_relation 表，检查 referrer_id 是否是 referred_id 的被推荐人

规则6：核销记录必须关联到具体员工账号
 实现：核销接口必填参数 verifier_id，从商家端登录态获取，不允许为空

规则7：余额抵扣上限30%
 实现：余额核销接口校验 deduction_amount ≤ order_amount × 0.30
```

## 第八节：决策框架与触发条件

### 开发启动前的三个必须确认项

**确认项1（今天就要办）：微信支付分账服务商资质申请是否已启动**

微信支付分账子商户入驻周期约2–4周 [14]，是整个项目唯一不能靠加班压缩的时间节点。入驻审核本身1–3个工作日，但账户验证、签约、测试环境联调加在一起实际周期2–4周。今天不启动，上线日期就推迟2–4周。入驻需要企业主体，因此先确认公司是否已注册。

**确认项2：开发团队是否有微信支付分账服务商模式的实际经验**

这是筛选开发团队的第一道门槛。微信支付分账的服务商模式接入是整个项目技术门槛最高的部分，没有做过的团队会在这里踩坑。面试时直接问："你们做过微信支付分账服务商模式接入吗？分账失败的重试机制怎么做的？"能答出来才考虑合作。

**确认项3：公司主体是否已注册**

微信支付分账需要企业主体，个人无法申请服务商资质。如果公司尚未注册，这是第一步。

### MVP验收的5个核心测试用例

**测试用例2（幂等控制）**：顾客C重复扫码3次 → 只触发1次欢迎语 → 只发放1张券（第2、3次领券请求返回已有券ID）

## 第二节：多维度完整性审查——9个维度逐一过堂

### 维度1：用户体验与引导流程的细节漏洞

**问题1：首次进入授权弹窗设计缺失**
微信小程序获取openid无需用户授权，但获取手机号必须由用户主动点击"获取手机号"按钮触发——不能在页面加载时自动弹出，否则会被微信审核拒绝 [5]。当前设计没有明确这个授权时机。
- **风险后果**：如果开发时在错误时机请求手机号，小程序直接审核不通过，上线被阻断。
- **补充方案**：手机号授权入口只在用户主动点击"领取优惠券"时触发，且必须使用微信官方的`<button open-type="getPhoneNumber">`组件，不能用自定义弹窗。openid在用户进入小程序时由后端通过code换取，无需用户操作。
- **优先级**：MVP必须

**问题2：燎小星打扰边界未定义**
当前设计"每会话最多弹出2次"，但没有定义"同一用户当日多次进入"的场景。如果顾客结账后再次打开小程序查余额，燎小星再次弹出欢迎语会让人烦躁。
- **风险后果**：打扰感降低扫码率和AI晒圈参与率。
- **补充方案**：燎小星自动弹出的触发条件精确为：同一`user_id`+同一`store_id`，距上次弹出超过4小时。同日内第2次进入只在用户主动点击燎小星头像时响应，不自动弹出。
- **优先级**：MVP必须

**问题3：AI晒圈上传失败无降级体验**
用户上传照片后调用通义万相API，但通义万相V2版只支持异步调用，不支持HTTP同步调用 [6]。当前设计按同步处理，会导致接口直接报错。
- **风险后果**：AI晒圈功能在生产环境完全失效，核心功能无法使用。
- **补充方案**：前端提交照片后显示"燎小星正在帮你想台词…"的等待动画（轮询后端任务状态，最长等待8秒）；若8秒内未完成，降级为纯文案海报（背景使用预设模板图，不调用图片生成API）；若通义千问也超时，展示3套预设文案供用户选择。降级时前端标注`is_fallback=true`，后端记录降级率用于监控。
- **优先级**：MVP必须（不解决则AI晒圈功能无法上线）

**问题4：余额抵扣码15分钟有效期在排队场景可能不够**
餐厅高峰期排队结账可能超过15分钟，顾客提前生成抵扣码后码过期，需要重新生成。
- **风险后果**：顾客在收银台操作失败，影响体验，店员也会感到麻烦。
- **补充方案**：将抵扣码有效期延长至30分钟；同时设计"码已过期"的友好提示和一键重新生成入口（重新生成不消耗次数限制）。
- **优先级**：MVP必须

**问题5：老年用户引导设计缺失**
当前设计假设用户熟悉微信小程序操作。60岁以上顾客可能不知道如何"扫码进小程序"，更不会主动上传照片。
- **风险后果**：老年客群扫码率接近零，影响门店整体扫码率数据，商家会认为系统没效果。
- **补充方案**：桌牌文案设计要极简，主文案只有一句话："扫一下，有券"；店员培训话术加一条："帮老人家扫一下，有优惠"；小程序内的AI晒圈入口不强制，可以跳过直接到余额页。微信小程序无障碍设计指南要求导航明确、减少等待、反馈及时 [7]，按此标准设计字体不小于16px，按钮点击区域不小于44×44px。
- **优先级**：可迭代（第2个月）

### 维度2：技术架构的遗漏细节

**问题1：通义万相V2只支持异步调用（高危，重复强调）**
通义万相V2版API不支持HTTP同步调用 [6]，必须用异步任务队列处理图片生成。当前PRD按同步设计，开发完成后会立刻发现这个问题。
- **补充方案**：后端实现任务队列：用户提交照片→生成`task_id`→返回给前端→前端每2秒轮询`GET /api/ai/task/{task_id}`→任务完成后返回海报URL。通义千问Plus基础限流500 QPM [8]，正常餐饮场景不构成瓶颈，但需在Redis中维护并发任务数上限（建议每门店同时最多5个AI任务）。

**问题2：Redis分布式锁必须用原子操作**
推荐关系绑定使用分布式锁，如果用`SETNX`+`EXPIRE`两条命令分开执行，存在服务宕机导致死锁的风险 [9]。
- **补充方案**：必须使用`SET key value NX PX 3000`单条命令（原子操作），锁超时3秒，避免死锁 [9]。

**问题3：微信URL Scheme参数长度限制**
小程序URL Scheme的QUERY参数最大512个字符 [10]，只支持数字、大小写英文及部分特殊字符。如果referrer_id使用UUID（36字符）加上store_id、table_id等参数，容易超限。
- **补充方案**：referrer_id改用6–8位Base62编码短ID（如`A3k9Bx`），store_id同样使用短ID，URL参数总长度控制在200字符以内，留足余量 [11]。

**问题4：图片存储方案未定义**
用户上传的原始照片和AI生成的海报存储位置未明确。如果直接存在服务器本地，扩展性差且有丢失风险。
- **补充方案**：使用阿里云OSS或腾讯云COS存储图片，配置CDN加速。用户上传照片临时存储7天（生成海报后即可删除原始照片，减少存储成本）；生成的海报永久存储（用户可能后续找回）。文件命名规则：`store_id/user_id/timestamp.jpg`，按门店分目录管理。

**问题5：服务通知（模板消息）发送条件**
微信小程序模板消息默认调用上限为10万次，系统根据粉丝量动态调整 [12]。更关键的是，服务通知需要用户在小程序内触发特定行为（如支付、表单提交）后才能发送，不能主动推送。
- **补充方案**：余额到期提醒、升级通知等消息，需要用户在小程序内有过"触发行为"才能发送。建议在领券成功时预先获取一次订阅消息授权（`wx.requestSubscribeMessage`），用于后续到期提醒。每类通知只申请一次授权，不要在用户每次操作时都弹授权弹窗。

**问题6：日志系统缺失**
当前PRD没有定义日志系统。上线后出了问题（如分账失败、核销异常）无法快速定位。
- **补充方案**：所有资金相关操作（核销、分账、余额变动）必须写结构化日志，包含`timestamp`、`user_id`、`store_id`、`operation_type`、`amount`、`result`、`error_code`。日志保留180天，支持按`user_id`或`order_id`检索。
- **优先级**：MVP必须

### 维度3：合规与法律的遗漏细节

**问题1：用户协议和隐私政策是上架必须条件**
微信小程序上架审核要求必须有用户协议和隐私政策入口，且必须在用户首次使用前展示 [5]。当前设计在"我的页面"有入口，但没有明确"首次进入强制展示"的逻辑。
- **补充方案**：用户首次进入小程序时，在进入主页前强制展示"用户协议与隐私政策确认弹窗"，用户点击"同意"后才能继续使用。弹窗包含两个链接：《用户服务协议》和《隐私政策》。后端记录`user.agreement_accepted_time`字段，未同意的用户无法使用任何功能。

**问题2：个人信息保护法（PIPL）合规要求**
收集手机号和消费记录需要明示告知目的 [13]。当前设计收集了手机号（用于会员识别）、消费记录（用于成长值计算）、位置信息（门店定位），这三类数据需要在隐私政策中逐一说明。
- **补充方案**：隐私政策必须包含：收集的数据类型（openid、手机号、消费记录、推荐关系）、收集目的（会员服务、返现计算、老带新奖励）、数据保留期限（账户注销后30天内删除）、用户权利（查询、导出、删除）。在"我的"页面提供"数据导出"和"注销账户"入口 [13]。

**问题3：广告法合规——话术绝对化用语**
燎小星话术中如果出现"最优惠""第一""绝对"等绝对化用语，违反《广告法》第九条，可能被投诉或被微信审核拒绝。
- **补充方案**：建立话术审核机制，所有燎小星话术模板在发布前过广告法敏感词过滤器。禁止词汇包括：最、第一、绝对、唯一、无与伦比、史上最低等。替代表达：用"特别划算""今天有福利""限时优惠"等相对化表述。

**问题4：微信小程序金融类功能审核标准更严**
涉及余额账户和分账功能的小程序，微信审核会要求提供相关资质说明 [5]。余额账户如果被认定为储值功能，可能要求提供金融类资质。
- **补充方案**：在小程序审核材料中明确说明：余额为"消费奖励积分"而非储值，不可提现，不可转让，有效期180天，属于营销活动权益而非金融产品。在用户协议中同样明确这一定性 [3]。如果审核方提出质疑，准备一份说明函，引用商务部预付卡管理办法中关于"消费奖励"与"预存资金"的区别 [3]。
- **优先级**：MVP必须（上架前必须准备好审核材料）

### 维度4：资金安全的遗漏细节

**问题1：退款场景的完整处理缺失（高危）**
当前设计没有覆盖退款场景。顾客消费100元，获得8元返现；次日申请退款；这8元返现是否追回？老带新返利10元是否追回？
- **风险后果**：如果不追回，商家实际上是在用自己的钱给顾客发奖励，但顾客并没有真实消费，直接导致商家资金损失。
- **补充方案**：退款场景处理逻辑：① 顾客申请退款→商家在商家端确认退款→系统触发退款回调；② 检查该订单对应的返现余额是否已被使用：若未使用，直接从余额账户中扣除；若已使用，标记为"待追回"，在该用户下次消费时优先抵扣；③ 检查是否触发了老带新返利：若推荐人余额未使用，同样扣除；若已使用，同样标记待追回；④ 退款回调必须与余额冲减在同一事务中执行，不允许分开处理。
- **优先级**：MVP必须

**问题2：商家账户余额不足时的分账失败处理**
微信支付分账需要商家账户有足够余额。如果商家当日营业额很低，但有大量老带新返利需要发放，可能出现余额不足导致分账失败。这与接口超时的失败不同，重试不会解决问题。
- **补充方案**：分账失败后，查询失败原因：若是余额不足（错误码`INSUFFICIENT_FUND`），写入`manual_queue`并标记原因为"余额不足"，不进入自动重试队列；平台运营收到告警后，联系商家补充余额，再手动触发补偿分账。
- **优先级**：MVP必须

**问题3：余额过期后的资金归属**
顾客180天内未使用的余额过期后，这笔钱的归属没有定义。
- **补充方案**：过期余额在系统中标记为`expired`，不退还给商家（因为这是商家的营销成本，相当于发出去的优惠券过期），也不由平台留存。在用户协议中明确：过期余额作废，不予补偿。过期前7天、3天、1天分别推送提醒（需预先获取订阅消息授权）。
- **优先级**：可迭代（上线初期余额有效期180天，1个月内不会有到期问题）

**问题4：大额异常核销的人工审核流程**
当前设计有异常核销检测（单日核销超阈值触发告警），但没有定义"谁来审、多久内处理、处理结果如何通知"。
- **补充方案**：异常核销触发条件（任一满足即触发）：同一`user_id`单日核销金额超过500元；同一`verifier_id`单日核销笔数超过30笔；同一`user_id`在同一门店单日核销次数超过3次。触发后：系统冻结该笔核销的分账（不发放返现和返利），推送告警给平台运营（通过企业微信机器人或邮件）；运营人员48小时内处理；处理结果（放行/驳回）通过商家端通知商家和顾客。
- **优先级**：MVP必须（基础规则），可迭代（规则完善）

**问题5：商家突然倒闭时顾客余额的处理**
商家停止营业后，顾客账户里有未用完的余额无法使用。
- **补充方案**：在平台服务协议（与商家签订）中约定：商家停用系统前30天必须通知平台；平台向所有有余额的顾客发送提醒；商家停用后余额展示保留，标注"该门店已暂停服务"；在用户协议中明确余额为门店营销权益，门店停业时平台协助协调但不承担兑付责任。MVP阶段先在合同中约定，系统层面第2–3个月迭代实现自动提醒。
- **优先级**：可迭代

### 维度5：商家运营边界的遗漏细节

**问题1：商家修改返现比例后，已发放余额如何处理**
商家将返现比例从8%调低至5%，之前已发放给顾客的8%余额是否受影响？
- **补充方案**：已发放余额按发放时的比例锁定，不受后续配置修改影响。余额账户中每笔记录都关联`cashback_rate_at_issue`字段，记录发放时的比例，与当前配置解耦。配置修改只影响修改后产生的新核销。
- **优先级**：MVP必须（否则会引发顾客投诉）

**问题2：删除员工账号后历史核销记录保留**
商家删除某个员工账号后，该员工的历史核销记录应该保留，否则对账数据不完整。
- **补充方案**：员工账号只做软删除（`status=disabled`），历史核销记录中的`verifier_id`字段保留，查询时显示"已离职员工"。禁止物理删除员工账号。
- **优先级**：MVP必须

**问题3：商家更换店长时的权限转移**
当前设计没有覆盖"老板想把店长权限从A转给B"的场景。
- **补充方案**：在商家端"员工管理"页面，老板（`role=owner`）可以将任意员工的角色从`manager`升降为`staff`，或从`staff`升为`manager`。权限变更实时生效，变更记录写入审计日志。企业微信群的群主转移需要线下操作（企业微信本身支持群主转让），系统层面只管理小程序内的权限。
- **优先级**：可迭代（第2个月）

**问题4：门店暂停营业期间的余额到期提醒**
门店装修暂停营业期间，系统仍会向顾客发送"余额即将到期"的提醒，但顾客无法到店消费，体验很差。
- **补充方案**：在商家端增加"暂停营业"开关（含预计恢复日期）。暂停期间：① 暂停发送余额到期提醒；② 顾客的余额有效期自动顺延（暂停天数不计入有效期）；③ 恢复营业后，重新开始计时并发送一次"门店已恢复营业"的通知。
- **优先级**：可迭代（第2–3个月）

**问题5：老板账号离职后的权限回收**
如果某家门店的"老板"角色账号换人了（如转让门店），原老板的账号需要被回收。
- **补充方案**：平台运营后台提供"门店owner账号变更"功能，需要原owner和新owner双方确认（或通过平台客服处理）。原owner账号变更为`disabled`，新owner账号绑定门店。此功能由平台运营人工处理，不需要在MVP阶段做自助化。
- **优先级**：可迭代

### 维度6：数据一致性与异常恢复

**问题1：网络中断时推荐关系写入状态不确定**
顾客扫码后网络断开，推荐关系可能处于"已写入数据库但响应未返回给前端"的状态，前端会认为失败并重试，导致重复写入尝试。
- **补充方案**：推荐关系绑定接口设计为幂等——使用`INSERT... ON CONFLICT DO NOTHING`，同一`(referred_id, store_id)`的重复写入直接返回已有记录。前端重试时收到相同的成功响应，不产生副作用。
- **优先级**：MVP必须

**问题2：核销接口超时的状态确认**
店员扫码核销后小程序卡住，顾客已离开。店员不知道是否核销成功，如果重新核销会导致重复扣减余额。
- **补充方案**：核销接口返回超时（前端等待超过5秒）时，前端自动调用`GET /api/store/verify/status?order_id=xxx`查询核销状态；若已核销，显示"核销成功（已完成）"；若未核销，提供"重新核销"按钮。核销接口本身也需要幂等设计：同一`coupon_code`只能核销一次，重复核销返回"已核销"而非报错。
- **优先级**：MVP必须

**问题3：成长值与等级不一致（部分失败场景）**
如果核销事务中成长值写入成功但等级更新失败（如数据库连接在两次写入之间断开），会出现成长值已达升级阈值但等级未更新的状态。
- **补充方案**：成长值更新和等级检查必须在同一数据库事务中执行（不是同一服务调用，而是同一SQL事务）。如果事务失败，整体回滚，不会出现部分成功状态。另外，增加一个每日凌晨运行的数据修复任务：扫描所有`growth_value >= next_level_threshold`但`current_level`未更新的记录，自动修复。
- **优先级**：MVP必须

**问题4：AI生成海报后用户未保存就关闭小程序**
用户生成了海报但没有点"保存到相册"就关闭了小程序，下次进来能否找回？
- **补充方案**：`ai_requests`表中保存`generated_image_url`，有效期30天（OSS设置30天后自动删除）。用户下次进入AI晒圈页面时，系统查询最近30天内的生成记录，若有未保存的海报，显示"你上次生成的海报还在，要保存吗？"的提示。
- **优先级**：可迭代（第2个月）

**问题5：余额流水与实际余额不一致的对账机制**
如果数据库出现异常（如磁盘满、主从延迟），可能出现余额流水记录了+8元但账户余额没变的情况。
- **补充方案**：每日凌晨运行对账任务：对每个`balance_id`，计算`SUM(transactions where type=credit) - SUM(transactions where type=debit)`，与`store_credit_accounts.available_amount`比对；不一致时写入告警日志，平台运营次日处理。同时，余额更新采用乐观锁（`UPDATE... WHERE available_amount = old_amount`），失败时重试，防止并发扣减导致不一致。
- **优先级**：MVP必须（基础对账），可迭代（自动修复）

### 维度7：扩展性与多商家隔离

**问题1：A商家员工能否访问B商家数据（高危）**
当前设计中所有接口都有`store_id`参数，但没有明确说明后端是否验证"当前登录用户的store_id是否与请求的store_id一致"。
- **风险后果**：如果验证缺失，A商家的店员可以通过修改请求参数访问B商家的会员数据，属于严重数据泄露。
- **补充方案**：所有商家端接口，后端必须验证JWT token中的`store_id`与请求参数中的`store_id`一致，不一致直接返回403。这个验证在中间件层实现，不依赖每个接口单独处理。
- **优先级**：MVP必须

**问题2：同一顾客在不同商家的账户独立还是共享**
顾客A在牛里牛气有会员账户，在另一家火锅店也有燎客系统的会员账户。openid相同，但store_id不同。
- **补充方案**：明确设计为完全隔离：同一openid在不同store_id下有独立的`member`记录、独立的`store_credit_account`、独立的`coupon_records`。唯一共享的是`users`表中的基础信息（openid、手机号）。这样商家A的数据对商家B完全不可见，符合商家的数据主权预期。
- **优先级**：MVP必须（架构决策，开发前必须明确）

**问题3：套餐到期后的数据保留策略**
商家停止付费后，数据保留多久？
- **补充方案**：套餐到期后30天内数据完整保留（商家可能忘了续费）；30–90天标记为"暂停状态"，数据只读不可操作；90天后归档（数据仍存储但不在主库中，需要申请才能恢复）；1年后永久删除。在套餐到期前7天、3天、1天分别发送续费提醒。
- **优先级**：可迭代（第3个月）

**问题4：接入第100家商家时的架构压力**
当前单库单表设计，100家商家、每家约1,000名会员，合计约10万条会员记录，对MySQL来说完全没有压力。但如果快速增长到1,000家，需要考虑分库分表。
- **补充方案**：MVP阶段不需要分库分表，但建议在`members`、`store_credit_transactions`、`orders`等大表上按`store_id`建立分区索引。当单表记录超过500万行时，再评估分库分表方案。
- **优先级**：监控观察

### 维度8：燎小星IP的内容安全

**问题1：AI生成文案中的违禁词**
通义千问生成的文案可能包含广告法违规词汇（最、第一、绝对）或其他违禁内容（涉政、涉黄）。
- **风险后果**：用户发出带违禁词的海报，平台可能被追责；微信/小红书可能封禁相关内容，影响老带新效果。
- **补充方案**：AI生成文案后，后端调用违禁词过滤接口（可使用阿里云内容安全API或自建词库）。过滤通过后才返回给前端；过滤不通过则重新生成一次（最多重试2次）；2次后仍不通过则降级为预设文案模板。
- **优先级**：MVP必须

**问题2：用户上传照片中的违规内容**
用户上传的照片可能包含违规内容（涉黄、涉政、版权图片等）。
- **补充方案**：用户上传照片后，后端先调用图片内容审核API（阿里云内容安全或腾讯云天御），审核通过后才进行AI处理。审核不通过时，返回"照片不符合要求，请更换"，不显示具体原因（避免用户绕过）。图片审核结果记录在`ai_requests`表中（`image_audit_result`字段）。
- **优先级**：MVP必须（否则平台有内容合规风险）

**问题3：燎小星话术远程更新机制**
当前话术模板硬编码在代码中，每次修改话术都需要发版。餐饮场景的话术需要经常调整（节日特供、新品上市等）。
- **补充方案**：话术模板存储在数据库中（`message_templates`表），前端通过接口拉取。平台运营在后台修改话术后，前端下次拉取时生效，不需要发版。话术模板按`store_type`（火锅/烧烤/咖啡等）和`trigger_event`（入群/领券/升级等）分类管理。
- **优先级**：MVP必须（否则每次调整话术都要重新发版审核，周期太长）

**问题4：不同餐饮品类的话术差异**
火锅店和咖啡馆的燎小星说话风格应该不同（火锅：热情豪爽；咖啡：文艺轻松）。
- **补充方案**：商家在入驻时选择门店品类（`store_type`），系统根据品类自动匹配话术风格模板。MVP阶段提供3套默认风格：热辣型（火锅/烧烤）、清新型（咖啡/简餐）、通用型。商家可以在后台预览并切换风格。
- **优先级**：可迭代（第2个月）

**问题5：顾客投诉AI生成内容侵权的处理流程**
AI生成的海报背景图可能与某些品牌图片相似，顾客发出后被指侵权。
- **补充方案**：在用户协议中明确：AI生成内容的知识产权归平台所有，用户获得个人使用授权；平台对AI生成内容的原创性不作保证；收到侵权投诉后，平台在24小时内下架相关内容模板。使用通义万相生成的图片，需确认阿里云服务条款中关于商业使用授权的条款。
- **优先级**：可迭代（第1个月运营后补充）

### 4.2 产品概述

**产品定位（一句话）**：燎客AI是专为线下中小餐饮门店设计的桌边私域裂变系统，把每一桌真实到店顾客变成免费的内容传播者和拉新引擎。

**核心价值主张**：
- **对顾客**：消费有返现（省钱），分享有奖励（赚钱），余额有身份感（铁杆会员更高权益）
- **对商家**：老带新成本约10–15元/单（低于平台投流），数据可见、ROI可算，不需要增加运营人员
- **对平台**：SaaS订阅费（699元/月/店）+ 数据网络效应，商家迁移成本随使用时间线性增加

**技术依赖清单**：
- 微信支付分账（服务商模式）：消费返现和老带新返利的资金流动底座，单笔比例上限30% [1]，入驻周期2–4周 [4]
- 通义千问Plus API：AI晒圈文案生成，成本约0.002–0.004元/次，限流500 QPM [8]
- 通义万相API（V2，异步调用）：AI晒圈图片生成，成本0.16元/张 [14]，仅支持异步调用 [6]
- Redis：分布式锁（推荐关系并发控制，必须用`SET key value NX PX`原子操作 [9]）、AI用量计数器（TTL自动过期）
- 阿里云OSS/腾讯云COS：图片存储，配CDN加速
- 内容安全API（阿里云或腾讯云）：AI文案违禁词过滤、用户上传图片审核

### 4.4 用户端（小程序用户版）完整PRD

#### 模块1：扫码进入与身份识别

**功能说明**：顾客扫桌牌二维码进入小程序，系统解析URL参数中的推荐关系，完成身份识别和推荐关系绑定。

**完整交互逻辑**：

```
用户扫码 → 解析URL参数（store_id, table_id, ref=referrer_id）
 ↓
检查是否首次进入小程序
 ├── 是：弹出《用户协议与隐私政策》确认弹窗
 │ 用户点击"同意" → 记录agreement_accepted_time → 继续
 │ 用户点击"不同意" → 停留在协议页，无法继续使用
 └── 否：直接继续
 ↓
code换取openid（后端静默完成，用户无感知）
 ↓
检查是否有ref参数（推荐人ID）
 ├── 有ref：调用推荐关系绑定逻辑（见4.8节）
 └── 无ref：直接进入
 ↓
创建/更新用户会话（session_id = UUID，有效期24小时）
 ↓
进入首页，触发燎小星欢迎逻辑（见模块2）
```

**边界情况处理**：
- URL参数中`ref`为用户自己的ID → 忽略，不绑定（防自我邀请）
- 推荐关系已存在（首次绑定优先）→ 忽略新的ref参数，不覆盖
- 推荐关系绑定后30天内未消费 → 自动过期，状态变为`expired`
- 网络断开后重新进入 → 幂等处理，不重复绑定

**字段定义**：

| 字段名 | 类型 | 必填 | 说明 |
|-------|-----|-----|-----|
| `user_id` | VARCHAR(32) | 是 | 系统内部用户ID（Base62编码，8位） |
| `openid` | VARCHAR(64) | 是 | 微信openid，唯一标识 |
| `store_id` | VARCHAR(16) | 是 | 门店ID（来自URL参数） |
| `table_id` | VARCHAR(16) | 否 | 桌台ID（来自URL参数，仅用于统计） |
| `referrer_id` | VARCHAR(32) | 否 | 推荐人user_id（来自URL参数ref字段） |
| `entry_source` | ENUM | 是 | `direct`/`referral_poster`/`referral_link` |
| `session_id` | VARCHAR(64) | 是 | 当次会话ID |
| `agreement_accepted_time` | DATETIME | 否 | 用户同意协议时间（NULL=未同意） |
| `today_verified` | BOOL | 否 | 当日是否有核销记录（控制AI晒圈激活，从Redis读取） |

**错误处理**：
- `store_id`不存在 → 展示"门店不存在或已停用"页面
- 协议未同意 → 无法进入任何功能页面，仅显示协议确认页

#### 模块2：燎小星欢迎与领券

**功能说明**：燎小星在首页以悬浮气泡形式引导用户领取到店券，控制打扰频率，确保体验不令人反感。

**完整交互逻辑**：

```
进入首页
 ↓
检查燎小星弹出条件（同时满足以下全部）：
 ① 本次会话内尚未弹出过（session维度）
 ② 距上次弹出超过4小时（user_id + store_id维度，从Redis读取）
 ③ 用户未主动关闭过燎小星（user_preference.dismiss_lsxing = false）
 ├── 满足：1.5秒后自动弹出，话术见下
 └── 不满足：不弹出，用户可点击右下角燎小星头像手动召唤
 ↓
用户点击"领取优惠券"按钮
 ↓
检查手机号是否已绑定
 ├── 已绑定：直接发券
 └── 未绑定：弹出"获取手机号"授权按钮（微信官方组件）
 用户点击授权 → 获取手机号 → 绑定 → 发券
 用户拒绝授权 → 以openid作为唯一标识发券（不强制绑定手机号）
 ↓
调用领券接口（幂等）→ 返回券信息 → 展示"已领取"状态
```

**幂等控制**：同一`user_id` + `store_id` + `coupon_type` + 当日（北京时间自然日），只能领取1张同类型券。重复调用返回已有券的信息，不创建新券。

**打扰边界规则**：
- 自动弹出：同一`user_id`+`store_id`，距上次弹出超过4小时，且本会话内未弹出
- 手动召唤：用户点击燎小星头像，任何时候均可响应
- 永久关闭：用户点击弹窗右上角"×"，记录`user_preference.dismiss_lsxing=true`，后续不再自动弹出（但手动召唤仍有效）

**字段定义**：

| 字段名 | 类型 | 必填 | 说明 |
|-------|-----|-----|-----|
| `coupon_id` | VARCHAR(32) | 是 | 券唯一ID |
| `coupon_type` | ENUM | 是 | `checkin_discount`/`referral_reward`/`birthday`/`upgrade_gift` |
| `coupon_value` | DECIMAL(10,2) | 是 | 面值（元）或折扣率（0.95=95折） |
| `min_amount` | DECIMAL(10,2) | 是 | 使用门槛（0=无门槛） |
| `expire_time` | DATETIME | 是 | 过期时间 |
| `issue_trigger` | ENUM | 是 | `scan`/`referral_success`/`birthday`/`upgrade`/`activity` |
| `cashback_rate_at_issue` | DECIMAL(5,4) | 否 | 发放时的返现比例（用于退款追回计算） |

**错误处理**：
- 今日已领取 → 返回已有券信息，前端展示"今日券已领取"
- 门店活动已结束 → 返回"当前无可领取的优惠"
- 手机号授权失败 → 跳过手机号绑定，用openid继续（不阻断主流程）

#### 模块3：AI晒圈功能

**功能说明**：用户上传照片+输入心情文字，AI生成带专属邀请码的海报。激活条件：当日在本店有核销记录。

**完整交互逻辑**：

```
用户点击"AI晒圈"入口
 ↓
检查激活条件：today_verified = true（当日有核销记录）
 ├── 未激活：展示"先到店消费，再来晒圈赚奖励"提示，提示下方展示余额和会员入口
 └── 已激活：进入AI晒圈页面
 ↓
检查今日用量：Redis key = ai_count:{user_id}:{YYYYMMDD}，TTL至次日0点
 ├── 已达3次上限：展示"今日次数已用完，明天再来"
 └── 未达上限：继续
 ↓
用户上传照片（1–3张，单张最大5MB）
 ↓
后端调用内容审核API（图片）
 ├── 审核不通过：返回"照片不符合要求，请更换"（不显示具体原因）
 └── 审核通过：继续
 ↓
用户输入心情文字（选填，最多50字）+ 选择风格（热辣/清新/通用）
 ↓
用户点击"生成大片"
 ↓
后端创建AI任务：
 1. 调用通义千问Plus生成文案（同步，约1–2秒）
 2. 文案通过违禁词过滤（不通过则重新生成，最多2次）
 3. 调用通义万相V2生成背景图（异步，返回task_id）
 4. 生成用户专属小程序码（携带ref=user_id&store_id参数）
 5. 等待图片任务完成（前端每2秒轮询，最长等待8秒）
 ↓
图片生成完成：后端合成海报（文案+背景图+专属小程序码）→ 上传OSS → 返回海报URL
图片生成超时（>8秒）：降级为纯文案海报（预设背景模板+文案+专属小程序码）
 ↓
前端展示海报预览
 ↓
用户点击"保存到相册" → 调用wx.saveImageToPhotosAlbum
用户点击"分享" → 调用wx.shareAppMessage（携带海报图片）
 ↓
Redis计数器+1（ai_count:{user_id}:{YYYYMMDD}）
```

**字段定义**：

| 字段名 | 类型 | 必填 | 说明 |
|-------|-----|-----|-----|
| `ai_request_id` | VARCHAR(32) | 是 | 请求唯一ID（幂等键） |
| `user_id` | VARCHAR(32) | 是 | 用户ID |
| `store_id` | VARCHAR(16) | 是 | 门店ID |
| `input_photos` | JSON | 是 | 上传照片OSS URL列表（1–3张） |
| `input_text` | VARCHAR(50) | 否 | 用户输入心情文字 |
| `style_type` | ENUM | 是 | `hot`/`fresh`/`general` |
| `generated_image_url` | VARCHAR(512) | 否 | 合成海报OSS URL（完成后写入） |
| `referrer_qrcode_url` | VARCHAR(512) | 否 | 专属小程序码OSS URL |
| `task_status` | ENUM | 是 | `pending`/`processing`/`done`/`failed`/`fallback` |
| `is_fallback` | BOOL | 是 | 是否使用了降级方案（纯文案海报） |
| `image_audit_result` | ENUM | 是 | `pass`/`reject`/`review` |
| `daily_count` | INT | — | 当日已生成次数（从Redis读取，不存DB） |
| `create_time` | DATETIME | 是 | 创建时间 |

**错误处理**：
- 今日次数已用完（Redis计数≥3）→ 错误码`AI_DAILY_LIMIT_EXCEEDED`，提示"今日次数已用完，明天再来"
- 图片审核不通过 → 错误码`IMAGE_AUDIT_FAILED`，提示"照片不符合要求，请更换"
- AI服务全部超时 → 降级为预设文案+模板背景，标记`is_fallback=true`

#### 模块4：燎客余额账户

**功能说明**：展示消费返现余额和老带新返利余额（合并为"燎客余额"），支持结账时出示抵扣码。余额不可提现，仅限本店消费抵扣。

**完整交互逻辑**：

**余额展示页**：
- 大字显示可用余额（`available_amount`）
- 红色标注即将过期金额（14天内到期的余额，`expiring_amount`）
- 次要展示：累计获得 / 已使用
- 余额明细列表：每笔记录显示来源类型（消费返现/老带新奖励/余额抵扣）+ 金额 + 时间 + 关联订单号（后4位）

**抵扣码生成**：
- 用户点击"结账时使用" → 生成抵扣码（UUID编码为8位短码）→ 展示二维码
- 抵扣码有效期30分钟（从生成时起计），展示倒计时
- 到期前5分钟显示"即将过期"提示，提供一键刷新
- 同一用户同一时刻只能有一个有效抵扣码（生成新码时旧码自动失效）

**余额抵扣上限**：单笔抵扣金额不超过本单消费金额的30%（对齐微信支付分账上限 [15]）。前端展示可抵扣金额时自动计算上限，不允许用户手动输入超额金额。

**字段定义**：

| 字段名 | 类型 | 必填 | 说明 |
|-------|-----|-----|-----|
| `balance_id` | VARCHAR(32) | 是 | 余额账户ID（每个user_id+store_id唯一） |
| `account_type` | ENUM | 是 | `store_credit`（固定值，不可改） |
| `available_amount` | DECIMAL(10,2) | 是 | 当前可用余额（元），不可为负 |
| `expiring_amount` | DECIMAL(10,2) | 是 | 14天内即将到期的余额（元） |
| `total_earned` | DECIMAL(10,2) | 是 | 历史累计获得（元） |
| `total_used` | DECIMAL(10,2) | 是 | 历史累计使用（元） |
| `deduction_code` | VARCHAR(16) | 否 | 当前有效的抵扣码（8位短码） |
| `deduction_code_expire` | DATETIME | 否 | 抵扣码过期时间 |

**余额流水字段**：

| 字段名 | 类型 | 必填 | 说明 |
|-------|-----|-----|-----|
| `tx_id` | VARCHAR(32) | 是 | 流水唯一ID |
| `balance_id` | VARCHAR(32) | 是 | 关联余额账户ID |
| `tx_type` | ENUM | 是 | `cashback`/`referral_reward`/`deduction`/`expired`/`refund_clawback` |
| `amount` | DECIMAL(10,2) | 是 | 金额（正数=入账，负数=出账） |
| `order_id` | VARCHAR(32) | 否 | 关联订单ID |
| `cashback_rate_at_issue` | DECIMAL(5,4) | 否 | 发放时返现比例（退款追回用） |

| `create_time` | DATETIME | 是 | 交易时间 |

**错误处理**：
- 余额不足 → 错误码`INSUFFICIENT_BALANCE`，提示"余额不足，可用余额：X元"

- 抵扣金额超过30%上限 → 错误码`DEDUCTION_LIMIT_EXCEEDED`，提示"最多可抵扣X元（本单30%）"

#### 模块5：会员等级与成长值

**功能说明**：展示当前等级、成长值进度条、已解锁权益列表。升级时触发仪式感动画和燎小星通知。

**等级体系**：

| 等级 | 升级阈值 | 核心权益 | 活跃度门槛 |
|-----|---------|---------|---------|
| Lv1 普通会员 | 注册即得 | 入群见面礼、生日券 | 无 |
| Lv2 熟客 | 500成长值 | 工作日（周一至周四）95折 | 无 |
| Lv3 铁杆 | 2000成长值 | 全时段9折 + 新品试吃优先报名 | 无 |
| Lv4 黑金 | 5000成长值 | 全时段85折 + 每月赠招牌菜（需当月有消费） + 优先订座 | 当月至少1次核销记录 |

**成长值来源**：

| 行为 | 成长值增量 | 触发时机 |
|-----|---------|---------|
| 消费 | 消费金额（取整，1元=1成长值） | 核销成功，同一事务 |
| 到店核销 | +50 | 核销成功，同一事务（与消费成长值叠加） |
| 成功邀请新客首次消费 | +200 | 新客首次核销成功后 |
| AI晒圈带来新客核销 | +100（叠加在+200上，合计+300） | 新客首次核销且`entry_source=referral_poster` |

**升级触发逻辑**：核销接口成功回调 → 后端同步计算成长值（同一事务）→ 检查是否达到升级阈值 → 写入`upgrade_events`表 → 异步推送燎小星升级通知 + 下次打开小程序时展示升级动画。

**降级规则**：等级只升不降，成长值永久有效。Lv4黑金每月赠菜权益需当月有消费记录才激活（折扣权益无活跃度门槛）。

**字段定义**：

| 字段名 | 类型 | 必填 | 说明 |
|-------|-----|-----|-----|
| `member_id` | VARCHAR(32) | 是 | 会员ID（user_id + store_id的组合键） |
| `current_level` | ENUM | 是 | `lv1`/`lv2`/`lv3`/`lv4` |
| `growth_value` | INT | 是 | 当前成长值（只增不减） |
| `next_level_threshold` | INT | 是 | 下一等级所需总成长值（lv4时为NULL） |
| `pending_upgrade` | BOOL | 是 | 是否有待展示的升级动画（下次打开小程序时触发） |

#### 模块7：用户协议与隐私政策入口（合规必须）

**功能说明**：首次进入时强制展示确认弹窗；"我的"页面提供随时查阅入口；提供数据导出和账户注销功能。

**用户协议必须包含的条款**（MVP上线前法务审核）：
1. 余额性质声明：燎客余额为消费奖励积分，非储值资金，不可提现，不可转让，有效期180天
2. 老带新规则说明：一级分销，仅直接推荐人获得奖励，推荐关系绑定30天有效期
3. 退款条款：退款时已发放的返现余额和返利将被追回（若已使用则从后续消费中抵扣）
4. 门店停业说明：余额为门店营销权益，门店停业时平台协助协调但不承担兑付责任
5. 争议解决：适用中华人民共和国法律，争议提交[公司注册地]法院管辖

**隐私政策必须包含的条款** [13]：
1. 收集的数据类型：微信openid、手机号（可选）、消费记录、推荐关系、AI生成内容
2. 收集目的：会员服务、返现计算、老带新奖励、AI晒圈功能
3. 数据保留期限：账户注销后30天内删除，法律要求保留的数据除外
4. 用户权利：查询、导出、更正、删除个人数据（在"我的"页面提供入口）
5. 第三方共享：数据不与第三方商家共享，仅在同一门店内流通

### 4.5 商家端（小程序商家版）完整PRD

#### 模块1：登录与权限验证

**功能说明**：商家端通过微信openid识别身份，JWT token携带role和store_id，所有接口在中间件层验证权限。

**登录流程**：
- 老板首次登录：通过平台运营人员绑定（MVP阶段人工操作，后续可做自助入驻）
- 员工绑定：老板在商家端生成邀请码二维码 → 员工扫码 → 后端绑定`openid`到`employees`表，角色默认为`staff`
- Token刷新：access token有效期2小时，refresh token有效期7天，无感知刷新

**安全要求**：所有商家端接口必须验证：① JWT token有效且未过期；② token中的`store_id`与请求参数中的`store_id`一致；③ token中的`role`有权限访问该接口。三个条件任一不满足，返回对应错误码。

#### 模块2：首页经营概览

**功能说明**：老板/店长每天第一眼看到的经营数据，支持今日数据卡片 + 7天/30天趋势图 + 快捷入口 + 燎小星经营提醒。

**今日数据卡片（6个核心指标）**：

**燎小星经营提醒**：每日最多1条，示例："本月有3位铁杆会员生日，发张生日券试试"。点击可跳转对应操作页面。

#### 模块3：核销功能

**功能说明**：提供三种核销方式，所有核销记录必须关联员工账号（`verifier_id`），支持查询核销历史。

**三种核销方式**：

**方式一：扫码核销（主要方式）**
- 点击"扫码核销" → 调起微信扫一扫 → 扫顾客券码二维码
- 展示券详情（券名、面值、门槛、有效期、顾客昵称脱敏）
- 店员确认 → 调用核销接口 → 成功：显示"核销成功"；失败：显示具体错误原因

**方式二：手动输入券码**
- 输入8位短码 → 查询券信息 → 确认核销
- 适用于扫码不方便的场景（如顾客手机屏幕反光）

**方式三：余额抵扣核销**
- 扫顾客展示的抵扣码二维码
- 展示：顾客可用余额 + 本单金额（店员输入）+ 可抵扣金额（不超过本单30%）
- 店员确认抵扣金额 → 调用余额核销接口

**核销记录**：按时间倒序展示，支持按员工筛选（老板/店长可查全部，店员只查自己）。字段：核销时间、券类型/面值、顾客昵称（脱敏）、核销员工名。

**超时处理**：核销接口超时（>5秒）时，前端自动查询核销状态；若已核销显示"核销成功（已完成）"；若未核销提供"重新核销"按钮。

#### 模块4：会员管理

**会员列表**：
- 筛选条件：等级（全部/Lv1–Lv4）、最近到店（近7天/近30天/30天以上）、老带新数（≥1/≥3/≥5）
- 搜索：手机号后4位或昵称关键字
- 排序：最近到店时间（默认）/ 累计消费金额 / 老带新次数

**会员详情页（360°视图）**：
- 基本信息：昵称、手机（脱敏）、入会时间、当前等级、成长值
- 消费记录：到店时间、金额、核销员工（最近10条，支持查看更多）
- 老带新记录：带来了哪些人、首次消费时间、返利状态
- AI晒圈记录：累计生成次数、最近时间

#### 模块5：活动配置

**功能说明**：商家通过预设模板配置活动，发布后系统自动更新燎小星话术，无需手动干预。

**MVP提供的活动模板（4类）**：

| 模板 | 配置项 | 说明 |
|-----|------|-----|
| 老带新奖励（常驻） | 老客奖励金额/类型、新客首单优惠、每人每月上限 | 核心裂变机制，建议长期开启 |
| 生日礼 | 提前发送天数（3/5/7天）、礼品类型/金额 | 系统自动在会员生日前发送 |

#### 模块6：返现策略配置

**功能说明**：商家配置消费返现比例和老带新返利金额，系统实时校验分账比例上限，展示预计成本。

**配置项**：

| 配置项 | 类型 | 范围 | 说明 |
|-------|-----|-----|-----|
| `cashback_rate` | 滑动条 | 3%–15% | 消费返现比例 |
| `referral_reward` | 输入框（元） | 0–50元 | 每单老带新返利金额 |
| `new_customer_reward` | 输入框（元） | 0–30元 | 新客首单优惠券面值 |
| `monthly_cost_alert` | 输入框（%） | 默认12% | 月度成本预警阈值 |

**实时校验**：
- 分账比例验证：`cashback_rate + (referral_reward / avg_customer_price) ≤ 0.30`，超过30%时禁止保存，提示"超过微信支付分账上限，请调低参数" [15]
- 成本预警：基于本月已核销金额预估当月总返现成本；超过`monthly_cost_alert`时显示黄色警告；超过18%时显示红色警告并建议联系平台运营

#### 模块7：员工与权限管理

**功能说明**：老板管理员工账号和角色，支持添加、删除（软删除）、角色变更。

**添加员工**：生成邀请码二维码（有效期24小时，使用后失效）→ 员工扫码绑定 → 默认角色`staff`。

**删除员工**：软删除（`status=disabled`），历史核销记录保留，显示"已离职员工"标注。禁止物理删除。

**角色变更**：老板可将`staff`升为`manager`或将`manager`降为`staff`，实时生效，写入审计日志。

#### 模块8：套餐与续费

**功能说明**：展示当前套餐状态，提供续费和升级入口（仅老板可见）。

**展示内容**：套餐名称（成长版Pro）、月费（699元/月）、到期日期、剩余天数、续费按钮。

**到期提醒**：到期前7天、3天、1天分别通过服务通知提醒老板。到期后30天内数据完整保留，30天后进入只读模式。

#### 模块9：数据导出

**功能说明**：支持导出会员列表、活动报表、月度经营总表为Excel文件，通过服务通知发送下载链接。

**导出类型**：会员列表（含成长值、等级、消费记录）、活动报表（参与人数、转化率）、月度经营总表（扫码/发券/核销/老带新汇总）。

**导出流程**：选类型+时间范围 → 后台异步生成 → 1–3分钟后通过服务通知发送下载链接（需预先获取订阅消息授权）。

### 4.8 后台核心业务逻辑（伪代码级别）

#### 逻辑1：推荐关系绑定（防并发、防自我邀请、防循环）

```
function bindReferral(referred_id, referrer_id, store_id):
 // 防自我邀请
 if referrer_id == referred_id:
 return {success: false, reason: "SELF_REFERRAL"}
 
 // 检查推荐关系是否已存在（首次绑定优先）
 existing = SELECT * FROM referral_relations 
 WHERE referred_id=? AND store_id=? AND status='active'
 if existing:
 return {success: false, reason: "ALREADY_BOUND"}
 
 // 防循环邀请：检查referrer是否是referred的被推荐人
 reverse = SELECT * FROM referral_relations
 WHERE referrer_id=referred_id AND referred_id=referrer_id AND store_id=?
 if reverse:
 return {success: false, reason: "CIRCULAR_REFERRAL"}
 
 // 加分布式锁（原子操作，防并发写入）
 lock_key = "referral_lock:" + referred_id + ":" + store_id
 lock_result = Redis.SET(lock_key, "1", NX, PX, 3000) // 原子操作，3秒超时
 if NOT lock_result:
 return {success: false, reason: "CONCURRENT_REQUEST"}
 
 try:
 // 写入推荐关系（唯一约束兜底）
 INSERT INTO referral_relations 
 (referrer_id, referred_id, store_id, entry_source, bind_time, expire_time, status)
 VALUES (?, ?, ?, ?, NOW, NOW+30days, 'active')
 ON CONFLICT (referred_id, store_id) DO NOTHING
 
 return {success: true}
 finally:
 Redis.DEL(lock_key)
```

#### 逻辑2：核销回调处理（同一事务，含返现、成长值、升级、老带新）

```
function handleVerifyCallback(order_id, user_id, store_id, order_amount, verifier_id):
 // 获取门店当前配置快照
 store = SELECT * FROM stores WHERE store_id=?
 cashback_amount = order_amount * store.cashback_rate
 
 BEGIN TRANSACTION:
 // 1. 创建订单记录
 INSERT INTO orders (order_id, user_id, store_id, verifier_id, order_amount, 
 cashback_amount, cashback_rate_snapshot, status)
 VALUES (?, ?, ?, ?, ?, ?, store.cashback_rate, 'completed')
 
 // 2. 更新余额账户（乐观锁防并发）
 old_amount = SELECT available_amount, version FROM store_credit_accounts 
 WHERE user_id=? AND store_id=?
 UPDATE store_credit_accounts 
 SET available_amount = available_amount + cashback_amount,
 total_earned = total_earned + cashback_amount,
 version = version + 1
 WHERE user_id=? AND store_id=? AND version=old_amount.version
 if affected_rows == 0: ROLLBACK; RETRY (最多3次)
 
 // 3. 写入余额流水
 INSERT INTO store_credit_transactions 
 (tx_type='cashback', amount=cashback_amount, order_id=?, 
 cashback_rate_at_issue=store.cashback_rate, expire_time=NOW+180days)
 
 // 4. 更新会员成长值（同一事务）
 growth_increment = FLOOR(order_amount) + 50 // 消费成长值 + 到店奖励
 UPDATE members SET growth_value = growth_value + growth_increment,
 last_visit_date = TODAY,
 total_visit_count = total_visit_count + 1,
 total_spend_amount = total_spend_amount + order_amount
 WHERE user_id=? AND store_id=?
 
 // 5. 检查升级（同一事务）
 member = SELECT * FROM members WHERE user_id=? AND store_id=?
 new_level = calculateLevel(member.growth_value)
 if new_level != member.current_level:
 UPDATE members SET current_level=new_level, pending_upgrade=true
 INSERT INTO upgrade_events (member_id, old_level, new_level, trigger_order_id)
 
 // 6. 更新核销券状态
 UPDATE coupon_records SET status='used', used_at=NOW, order_id=?
 WHERE coupon_code=?
 
 COMMIT
 
 // 7. 异步处理老带新返利（事务外）
 ASYNC: triggerReferralReward(user_id, store_id, order_id, order_amount, store)
 
 // 8. 异步推送通知
```

#### 逻辑3：微信支付分账逻辑（含比例验证、失败重试）

```
function triggerReferralReward(referred_id, store_id, order_id, order_amount, store):
 // 查找有效推荐关系
 referral = SELECT * FROM referral_relations
 WHERE referred_id=? AND store_id=? AND status='active'
 AND expire_time > NOW
 if NOT referral: return
 
 // 检查是否是首次消费（防重复触发）
 order_count = SELECT COUNT(*) FROM orders WHERE user_id=referred_id AND store_id=?
 if order_count != 1: return // 只有首单触发
 
 // 计算分账比例验证（不超过30%）
 cashback_amount = order_amount * store.cashback_rate
 reward_amount = store.referral_reward
 total_ratio = (cashback_amount + reward_amount) / order_amount
 if total_ratio > 0.30:
 reward_amount = order_amount * 0.30 - cashback_amount // 取最大可用金额
 if reward_amount <= 0: return // 已无空间分账
 
 // 获取推荐人的微信支付账号
 referrer_wx_account = getWxPayAccount(referral.referrer_id)
 
 // 调用微信支付分账API
 result = WxPay.profitSharing(
 transaction_id=order_id,
 receivers=[{account: referrer_wx_account, amount: reward_amount}]
 )
 
 if result.success:
 // 写入推荐人余额
 updateBalance(referral.referrer_id, store_id, reward_amount, 'referral_reward')
 // 更新推荐关系状态
 UPDATE referral_relations SET status='consumed', first_order_id=order_id, 
 reward_amount=reward_amount, reward_paid_at=NOW
 // 更新推荐人成长值
 growth = 200
 if referral.entry_source == 'referral_poster': growth = 300
 UPDATE members SET growth_value = growth_value + growth
 // 推送通知给推荐人
 ASYNC: sendReferralRewardNotification(referral.referrer_id, reward_amount)
 else:
 // 写入重试队列
 INSERT INTO retry_queue (order_id, retry_type='referral_reward', 
 target_user_id=referral.referrer_id, amount=reward_amount,
 next_retry_at=NOW+5min, status='pending')
```

#### 逻辑4：反作弊规则引擎（12条规则）

```
反作弊规则列表（核销前检查，任一触发则标记suspicious）：

规则1：防自我邀请
 触发条件：referrer_id == referred_id
 处理动作：绑定失败，返回SELF_REFERRAL
```

### 4.10 非功能性需求

**性能要求**：
- 核销接口（`/api/store/verify/*`）响应时间 < 500ms（P99），因为店员在收银台等待，超时会直接影响顾客体验
- AI生成接口（`/api/ai/generate`）任务提交响应 < 1s（P99）；任务完成时间 < 8s（P95），超时降级
- 首页数据接口（`/api/store/dashboard`）响应时间 < 1s（P99）

**可用性要求**：
- 核心链路（扫码进入/核销/分账）99.9%可用（月度不可用时间 < 44分钟）
- AI晒圈功能99%可用（允许降级为纯文案海报）
- 数据库每日凌晨1:00–2:00允许10分钟维护窗口（此时段门店通常不营业）

**安全要求**：
- 所有接口必须通过JWT鉴权，商家端接口额外验证store_id归属
- 手机号使用AES-256加密存储，展示时脱敏
- 余额账户不开放提现接口（`account_type=store_credit`硬编码，后端不提供任何提现路径）
- Redis分布式锁使用`SET key value NX PX`原子操作 [9]
- 所有资金操作写结构化审计日志，保留180天

**合规要求**：
- 用户协议和隐私政策必须在首次使用前展示，用户同意后记录时间戳
- AI生成内容必须通过违禁词过滤和图片内容审核后才能返回给用户
- 推荐关系只存储一跳（数据库唯一约束），不存储间接层级
- 返利触发事件绑定在核销接口成功回调上，不在注册或扫码事件上触发
