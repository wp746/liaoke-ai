# 燎客 AI 三端高保真原型设计

> 日期：2026-07-10  
> 状态：用户已确认  
> 需求基线：`docs/PRD-liaoke-ai-mvp-v3.0.md` + `docs/PRD-liaoke-ai-mvp-v3.1-points.md`  
> 原型策略：方案 A——React/Vite 三端完整原型，确认后同步用户端与商家端核心页面到原生微信小程序

## 1. 设计目标

在现有燎客 AI 仓库、品牌资产和微信小程序骨架上，构建一套可运行、可点击、可用于产品评审和路演的高保真原型，覆盖：

1. 顾客使用的微信小程序用户端。
2. 老板、店长、店员使用的微信小程序商家端。
3. 创始人和平台运营使用的 Web 后台管理端。

原型必须完整表达从真实到店、会员沉淀、AI 分享、老带新、复购权益、积分兑换到商家与平台运营的业务闭环，不能退化为静态页面画廊。

## 2. 产品定位

燎客 AI 是餐饮门店的桌边私域增长系统。

它以桌牌扫码为入口，把到店顾客转化为门店会员、AI 内容创作者、推荐者和复购用户，并让商家能够核销、配置、追踪和复盘整条增长链路。

核心闭环：

```text
真实到店
→ 桌牌扫码
→ 会员沉淀
→ 到店权益
→ 消费核销
→ 返现/成长值/积分
→ AI 晒圈
→ 推荐关系绑定
→ 新客首次消费
→ 推荐人获得抵扣券
→ 推荐人再次复购
```

### 2.1 三方价值

- 顾客：领取到店福利、获得消费返现、积累等级和积分、生成 AI 分享内容、邀请朋友获得抵扣券。
- 商家：把已有堂食客流沉淀为会员，以可控成本提高复购、分享和老带新。
- 燎客平台：通过 SaaS 套餐、门店运营数据、行业模板和后续 AI 运营能力建立长期壁垒。

## 3. 目标用户与权限

### 3.1 顾客端

- 首次到店并扫描桌牌的新客。
- 已领取权益、准备复购的老客。
- 愿意拍照分享，但不会写文案或设计海报的用户。
- 对积分兑换饮品、小菜和服务有兴趣的高频用户。

### 3.2 商家端

| 角色 | 主要任务 | 导航能力 |
|---|---|---|
| `owner` 老板 | 看经营、管会员、配活动和权益、管理员工与续费 | 经营 / 核销 / 会员 / 运营 / 我的 |
| `manager` 店长 | 看数据、管会员、执行核销 | 经营 / 核销 / 会员 / 记录 |
| `staff` 店员 | 快速核销并查看本人记录 | 核销 / 记录 / 我的；登录后直接进入核销 |

### 3.3 平台后台

PRD v3.0 的 `platform_admin` 是跨门店只读角色，但平台后台同时需要创建门店、配置桌码和额度。为消除权限冲突，原型增加：

| 角色 | 权限 |
|---|---|
| `super_admin` | 创始人/超级管理员；可创建和编辑门店、桌码、套餐、配额、模板与账号 |
| `platform_admin` | 平台运营；跨门店只读，可查看经营、风险、续费和任务状态，不显示写入按钮 |

所有后台写操作在视觉上明确标注权限并进入审计日志。

## 4. 四套价值体系

用户端必须清楚区分以下体系：

| 体系 | 用途 | 产品约束 |
|---|---|---|
| 成长值 | 决定 Lv1–Lv4 等级 | 只升不降；不抵现金 |
| 返现余额 | 下次消费抵扣 | 不可提现；有抵扣比例和有效期 |
| 老带新抵扣券 | 朋友首次消费后给推荐人的复购权益 | T+0 发放、T+1 生效；不可提现 |
| 积分 | 兑换赠品或服务 | 不抵现金、不可提现、不可转让 |

设计不得把四种价值全部统称为“奖励”，也不得让积分出现现金抵扣表达。

## 5. 已确认的视觉母体

视觉方向采用 B「星火操作系统」。

### 5.1 视觉原则

- 大面积使用象牙白、奶油白和干净留白。
- 主行动使用 Ember 橙色渐变。
- 奖励和等级使用星光金。
- AI Cyan 只用于 AI 状态、生成进度和智能提示，不大面积铺底。
- 卡片圆润但不过度堆叠，信息层级主要依靠留白、字号和细边框。
- 用户端有温暖餐饮感；商家端和平台后台提高信息密度但保持同一品牌来源。

### 5.2 燎小星使用规则

用户端重点使用现有 3D 燎小星动作资产：

- 首页欢迎。
- 领券成功。
- AI 上传和生成。
- 海报完成。
- 积分与会员升级。
- 空状态、失败和安慰状态。

商家端与平台后台以操作效率为主，不常驻大幅吉祥物；只在经营建议、完成反馈和品牌空状态中使用缩小版燎小星或火星标识。

## 6. Galacean Effects 动效策略

Galacean Effects 只作为高价值反馈层，不成为页面布局依赖。

### 6.1 使用节点

1. 扫码进入后“火种点亮”。
2. AI 生成中的星火粒子和环形进度。
3. 领券成功的短时火花。
4. 会员升级的星轨揭示。
5. 积分兑换成功的礼遇反馈。
6. 海报生成完成时的火光揭示。

### 6.2 约束

- 延迟加载，不能影响首屏、领券、核销和保存海报。
- 列表、表格、核销确认、权限提示不加载 WebGL。
- 支持系统“减少动态效果”偏好。
- 加载失败时降级为 CSS 动画或静态品牌图。
- 原生微信小程序同步阶段根据运行能力选择兼容实现，不强行复制 WebGL 方案。

## 7. 三端信息架构

### 7.1 用户端导航

采用 A「权益分层型」：

```text
首页 / 权益 / AI创作 / 积分 / 我的
```

- 首页：门店身份、到店券主行动、AI 入口、积分和权益摘要。
- 权益：到店优惠券、老带新抵扣券、返现余额。
- AI创作：上传、风格、生成进度、结果和海报。
- 积分：积分账户、签到、明细、商城和兑换记录。
- 我的：等级成长值、邀请记录、资料、协议、数据权利和注销。

### 7.2 商家端导航

采用 A「角色化经营工作台」。

- 老板首页先呈现经营指标、成本状态、燎小星经营建议和快捷核销。
- 店长保留经营、核销、会员和本人/门店记录。
- 店员登录后直接进入核销，避免看到无权限配置。
- 核销入口在所有有核销权限的角色中保持固定位置。

### 7.3 平台后台布局

采用 A「全局经营指挥台」。

- 左侧：平台总览、门店、桌码、AI/提示词、权益模板、风险、套餐、导出、系统审计。
- 顶部：全局搜索、角色状态、消息和账号。
- 中间：平台 KPI、趋势、风险队列和门店列表。
- 右侧上下文抽屉：创建/编辑、配置、审核和任务详情。
- 门店表支持快速进入单店 360°详情。
- `platform_admin` 只读时隐藏创建、编辑、发布、停用等操作。

## 10. 原型技术结构

React/Vite 原型采用以下边界：

```text
Prototype Shell
├── Surface Switcher
│   ├── Customer Mini Program
│   ├── Merchant Mini Program
│   └── Platform Admin
├── Route Registry
├── Shared Design System
├── Domain Components
├── Scenario State Store
├── Mock Data Fixtures
└── Motion Layer
```

### 10.1 Prototype Shell

- 提供三端切换、页面目录、设备视口、场景选择和原型说明。
- 用户端、商家端使用小程序尺寸。
- 平台后台使用桌面布局并支持平板收缩。

### 10.2 Route Registry

- 每个页面有稳定 route id、所属端、角色权限和展示标题。
- 页面清单由注册表生成，避免导航和页面实现脱节。
- 允许从原型目录直接打开任意页面或状态。

### 10.3 Shared Design System

- 品牌 Token：颜色、字号、间距、圆角、阴影和动效节奏。
- 基础组件：按钮、卡片、标签、Tabs、列表、表格、弹窗、抽屉、空状态。
- 品牌组件：Logo Lockup、燎小星 Bubble、IP Feedback、AI Loading、Spark Success。

### 10.4 Domain Components

- Coupon Card / Coupon Code。
- Balance Card / Deduction Code。
- Points Product / Redemption Code。
- Member Level / Growth Progress。
- Verification Mode / Verification Result。
- Merchant KPI / Trend Chart。
- Store Table / Risk Event / Audit Entry。

### 10.5 Scenario State Store

原型使用可切换场景，而不是把展示数据写死在页面内部。建议场景：

- 新顾客首次扫码。
- 老客已领券。
- AI 生成成功。
- AI 超时降级。
- 新客触发推荐券。
- 店员执行积分兑换核销。
- 门店暂停营业。
- 平台出现异常核销和 AI 失败任务。

### 10.6 Mock Data Fixtures

- 顾客、会员、门店、员工、优惠券、返现余额、积分商品、兑换记录、订单、AI 任务、风险事件。
- 所有示例使用真实中文业务内容和合理数值。
- 不连接生产接口，不存储真实顾客信息。

## 12. 合规与文案边界

- 不写“发朋友圈才给优惠”或其他强制分享表达。
- 不把余额、积分和抵扣券描述为可提现资金。
- 不出现“下线”“团队收益”“拉人头计酬”等表达。
- 手机号授权只能在用户主动领券时触发。
- 用户端不出现“裂变”“私域”“获客”等 B 端术语。
- 积分兑换页面只表达赠品/服务，不显示现金折算。
- 平台运营只读角色不得出现可点击的写入操作。

## 13. 响应式与可访问性

- 用户端和商家端以 375–430 px 宽度为主，支持常见小程序安全区。
- 平台后台优先 1280–1600 px，平板宽度下折叠侧边栏。
- 所有主按钮有可读文本和足够点击区域。
- 图表颜色之外必须有文字或标签表达状态。
- 动效不承担唯一信息传递职责。
- 支持键盘访问后台导航、表格操作和弹窗。
- 尊重 `prefers-reduced-motion`。

## 14. 验收标准

1. 56 个核心页面和关键弹层全部可访问。
2. 五条主业务闭环可从头点击到底，不出现死路。
3. `owner`、`manager`、`staff`、`super_admin`、`platform_admin` 会真实改变导航和操作能力。
4. 用户端和商家端适配常见小程序尺寸；后台适配桌面和平板。
5. Galacean 动效可降级，不阻塞领券、核销、保存海报和后台操作。
6. 合规文案不出现强制分享、提现、团队收益等敏感表达。
7. 原型使用真实业务内容，不使用无意义 Lorem Ipsum。
8. 构建通过。
9. 关键页面完成截图验证。
10. 主流程完成交互冒烟验证。

## 15. 实施边界

本设计阶段交付的是高保真可交互原型，不包含：

- 生产数据库和真实支付能力。
- 通义万相/千问的正式 API 调用。
- 真实微信登录、手机号解密和服务通知。
- 生产级风控、定时任务和审计存储。
- 多门店连锁总部能力。
- 视频海报或强制分享功能。

原型确认后，用户端与商家端核心页面同步到现有 `miniprogram/` 骨架；平台后台继续作为 Web 应用演进。
