## 手册一：燎客内部员工快速上手手册（运营/销售合伙人）

### 第一章：燎客是什么——核心闭环一张图

**系统核心闭环**（文字版流程图）：

```
顾客扫桌牌二维码
 ↓
燎小星弹出欢迎语 → 顾客领取到店券
 ↓
顾客消费 → 店员扫码核销
 ↓
系统自动计算消费返现（cashback）→ 写入余额账户
 ↓
顾客进入AI晒圈 → 生成带专属推荐码的朋友圈海报
 ↓
朋友扫海报上的专属码进入小程序
 ↓
朋友首次消费核销（B的首单）
 ↓
系统T+0向老客（A）写入一张抵扣券（status=pending）
T+1（24小时后）生效，30天有效期，满30元可用
 ↓
老客下次来店出示抵扣券码 → 店员核销 → 抵扣成功
```

**两套激励机制的区别**（必须能向商家老板说清楚）：

- **消费返现（cashback）**：顾客自己消费后，系统按返现比例（默认8%）把钱写入顾客自己的余额账户。100元消费得8元余额，下次来店可最多抵扣本单30%。余额不可提现，有效期180天。
- **老带新抵扣券**：老客的朋友来消费后，系统给老客发一张抵扣券（默认10元面值，次日生效，30天有效期）。这是奖励老客的分享行为，不是奖励老客自己消费。

**v3.0关键变更——必须记住**：v3.0已完全删除微信支付分账接口，老带新返利通过数据库写入`referral_coupons`表实现，无需任何第三方支付入驻 [1]。原v2.0中分账接口、`retry_queue`表、分账重试定时任务均已删除，遇到有人问"分账入驻办了吗"——回答：v3.0不需要。

### 第二章：三天上线SOP——每天干什么

**Day 1（确认策略，约2小时）**

与商家老板逐项确认并书面记录：

| 配置项 | 默认值 | 可配置范围 | 确认签字 |
|--------|--------|-----------|---------|
| 消费返现比例 | 8% | 3%–15% | □ |
| 老带新抵扣券面值 | 10元 | 5–20元 | □ |
| 抵扣券有效期 | 30天 | 30/45/60天 | □ |
| 每人每月领取上限 | 10张 | 1–20张 | □ |
| 桌牌IP名称 | — | 商家自定（如"AI肉小签"） | □ |
| 门店品类 | — | 火锅/烧烤/咖啡/简餐/其他 | □ |
| 进店人次统计方式 | 收银台开单数 | 不得事后变更 | □ |

进店人次统计方式必须在试点开始前书面确认，试点结束后不得变更口径——这直接影响扫码率指标的计算，是试点合同第五条的核心数据基础。

**Day 2（系统配置+桌牌，约3小时）**

在商家端后台按顺序完成：
1. 门店基础信息录入（名称/品类/人均客单价/桌台数量）
2. 返现策略配置（按Day 1确认单填入，保存前检查成本预警是否触发）
3. 燎小星话术风格选择（热辣/清新/通用，可在后台预览效果后选择）
4. 生成桌台二维码（每桌一个，系统自动携带`store_id`和`table_id`参数）
5. 确认桌牌物料印刷完成：主文案"扫一下，领券+AI帮你做朋友圈大片"，字号不小于60pt
6. 摆放桌牌：放在顾客落座后视线高度，不被菜单遮挡

**Day 3（员工培训+正式上线，约1小时）**

- 30分钟员工培训（按手册二执行，重点：一句话话术+四种核销操作）
- 运营合伙人现场陪同完成第一个真实核销，确认全流程无误
- 上线后第一天每小时查看一次数据看板，确认扫码人数有数据写入（非零）
- 当日结束前检查：是否有`referral_coupons`表写入（若当日有老带新触发）

### 第三章：日常代运营工作节奏

**每日（约30分钟）**

登录商家端首页，检查6个核心指标：今日扫码人数、领券人数、新增会员、AI晒圈人数、老带新订单数、预估新增营业额。

重点关注两类告警（v3.0已删除分账失败告警，只剩这两类）：
- **AI算力成本告警**：当月门店AI调用总成本超过100元时系统推送。触发后检查Redis用量计数器是否有异常，必要时临时将每日上限从3次降至1次。
- **异常核销告警**：同一用户单日核销金额超500元、同一员工单日核销超30笔、同一用户单日核销超3次，任一触发则该笔分账暂缓，需人工处理。

**每周（约1小时）**

每周一凌晨2:00系统自动生成数据周报（定时任务），运营合伙人上午审核5分钟后确认发送给商家老板。周报包含：本周扫码人数、领券人数、老带新订单数、余额核销率、新增会员数，以及与上周同期的环比变化。

与商家老板每周沟通一次（电话或见面），收集反馈，重点问：顾客扫码体验有没有问题、店员有没有主动引导、有没有顾客投诉。

**每月（约2小时）**

整理月度经营总表，内容包含：全月扫码率（扫码人数÷进店人次）、老带新订单数、余额核销率、抵扣券核销率、预估带动营业额增量。

到期前30天启动续费沟通：准备续费数据报告（用月度总表数据），展示三项试点指标的实际达成情况，对照试点合同的承诺数字。

### 第四章：常见问题处理手册（Q&A）

**顾客说"扫不进去"**

处理流程：① 让顾客检查微信是否是最新版本；② 让顾客换一个网络（WiFi/4G切换）；③ 运营合伙人用自己手机扫同一桌牌验证是否是码本身的问题；④ 若码本身有问题，在商家端重新生成该桌台二维码并重新打印。记录问题桌台编号，当日内解决。

**顾客说"我的抵扣券不见了"**

先在商家端会员详情页查看该顾客的`referral_coupons`记录，判断状态：
- `status=pending`（待生效）：告知顾客"这张券是明天才生效的，今天还不能用，明天来就可以用了"
- `status=expired`（已过期）：告知顾客"这张券已经过期了，下次朋友来消费还会给您发新的"
- 找不到记录：确认朋友是否真的在本店首次消费核销过，若核销记录存在但券未写入，联系创始人处理

**店员误操作核销了怎么办**

MVP阶段无自动撤销功能，联系创始人人工处理。处理步骤：① 在`orders`表标记该订单`status=suspicious`；② 检查是否已触发cashback写入，若已写入则在`store_credit_transactions`表手动冲减；③ 检查是否已触发抵扣券发放，若已发放则将`referral_coupons`记录`status`改为`cancelled`；④ 全程留操作日志。

**商家说"扫码的人太少"**

先排查原因再给建议：① 检查桌牌摆放位置（是否被菜单或调料遮挡，是否在顾客落座后视线高度）；② 检查店员是否在主动引导（抽查2–3名店员，让他们当场复述核心话术）；③ 建议做文案A/B测试：把一半桌牌换成"扫一下，领10元券"，另一半保持"扫一下，AI帮你做朋友圈大片"，观察一周扫码率差异，用数据决定后续统一文案。

**商家说"想要多级分销"**

标准回应（口语化，不超过3句话）：
> "多级分销不是技术做不到，是法律不让做。三级以上分销触发传销刑事追诉门槛，我们在代码层面硬编码只存一跳，是主动选择，保护你也保护我。一级分销加上余额锁定，效果已经够用了。"

**AI晒圈生成失败怎么办**

系统已有自动降级机制：通义万相超时（>8秒）或API报错时，系统自动切换为纯文案海报（预设背景模板+AI生成文案+专属小程序码），用户收到"已为您生成文案版海报"提示 [2]。运营合伙人无需手动干预，记录`is_fallback=true`的比率，若连续一天内超过30%，联系技术合伙人检查通义万相API状态。

**商家问"这是不是传销"**

标准合规话术（见手册三第四章第5条）：
> "不是。传销认定需要同时满足三个条件：缴纳入门费、拉人头计酬、团队计酬。我们这套设计：零入门费，只有一级——老顾客带朋友来，老顾客得一张抵扣券；朋友再带他的朋友来，是朋友得券，不是老顾客再得一次。没有层级，没有入门费，符合《禁止传销条例》要求。" [3]

## 手册二：商家店员操作手册（通俗易懂版）

### 第一章：你只需要记住一句话

**（大字体，加粗，居中，打印时字号不小于36pt）**

> **"扫这个码有券，还能AI帮你做朋友圈大片。"**

为什么这句话有效：两个钩子缺一不可。只说"有券"——顾客觉得不过是普通优惠，不一定扫。只说"AI大片"——顾客不知道有什么好处，也可能懒得扫。两个一起说，即时利益（有券）加上好奇心（AI大片），扫码率能差出一倍。

### 第三章：四种核销操作步骤

**操作一：扫码核销到店优惠券**（最常用，每天用）

> 图示说明：打开商家版小程序首页，"扫码核销"按钮在屏幕中央最显眼位置，橙色大按钮。

1. 打开商家版小程序，点"扫码核销"
2. 对准顾客手机屏幕上的券码二维码扫描
3. 屏幕显示券信息（券名/面值/顾客昵称），确认无误后点"核销"，显示绿色"核销成功"

**操作二：手动输入券码**（顾客手机屏幕反光/扫不出来时用）

> 图示说明：首页"扫码核销"按钮下方有"手动输入"小字链接。

1. 打开商家版小程序，点"手动输入"
2. 让顾客报出手机上显示的8位短码，逐位输入
3. 点"查询"确认券信息，点"核销"

**操作三：余额抵扣核销**（顾客要用消费返现余额抵扣时）

> 图示说明：首页有独立的"余额核销"按钮，与"扫码核销"并排。

1. 打开商家版小程序，点"余额核销"
2. 扫顾客手机上的抵扣码二维码（顾客在"我的余额"页面生成，有效期30分钟）
3. 输入本单实际消费金额，屏幕自动显示可抵扣金额（最多抵扣本单30%），点"确认核销"

**操作四：老带新抵扣券核销**（v3.0新增，顾客用朋友消费换来的抵扣券时）

> 图示说明：首页有"抵扣券核销"按钮，图标是一张券的样式。

1. 打开商家版小程序，点"抵扣券核销"
2. 扫顾客手机"我的券包→老带新抵扣券"页面展示的二维码
3. 屏幕显示券面值（10元）和使用条件（满30元可用），本单金额满足条件后点"核销"

### 第五章：三条红线——绝对不能做

1. **不能用自己的账号给自己核销**。系统会检测核销员账号和顾客账号，同一人操作会被拦截，返回"不允许自我核销"。

2. **核销必须通过商家版小程序完成**，不能用其他任何方式（包括口头确认、截图等）代替系统核销。核销记录会关联到你的员工账号，是你的工作记录，也是老板查对账的依据。

3. **不要向顾客承诺"余额可以提现"**。余额和抵扣券只能在本店消费时抵扣，不能变成现金。说错了会引发顾客投诉，商家会追究责任。

### 第二章：让老板亲自扫一下（演示脚本）

这是整个谈判最重要的环节，比任何PPT有效十倍。

**第二步**：老板扫码后，站在旁边引导，不要抢手机：

- 领券时，说："顾客扫码就能领券，下次来消费直接用，不需要注册会员，扫码就是会员。"
- 进入AI晒圈时，说："让他拍一张照片，我们看看AI帮他做出来的是什么。"

**第三步**：演示完说："这就是你的顾客每次来店会看到的。他发出去，朋友来吃，你的老顾客第二天就能收到一张10元抵扣券，下次来用。整个过程你不需要做任何事，系统自动完成。"

## 第六节：8个自动化定时任务验收标准

所有定时任务须满足通用要求：**幂等性**（重复执行不产生副作用）、**失败告警**（任务失败写入日志）、**执行时间记录**（用于监控是否按时执行）。

### 任务T1：抵扣券激活任务（v3.0新增，P0）

| 字段 | 内容 |
|------|------|
| 执行频率 | 每小时（整点） |
| 触发条件 | `referral_coupons.status='pending' AND effective_time <= NOW` |
| 验收方法 | 手动插入一条`effective_time=当前时间-1分钟`的pending券，等待下一个整点任务执行 |

| 失败处理 | 通知发送失败时标记`notify_failed`，写入日志；SQL更新失败重试1次，仍失败写入告警 |

## 一、多维度审查：现有闭环还缺什么、要注意什么

### 1.1 闭环有没有大问题？

v3.0 的核心闭环是：

> 桌边扫码 → 领券 → 消费核销+返现（cashback） → AI晒圈 → 老带新 → 抵扣券发放 → 下次消费核销 → 数据自动沉淀

从产品、技术、合规三个角度看：  
- **产品逻辑**：链路完整，少一步都会塌，现在各环节都有对应数据表、接口和定时任务支撑，MVP 可以落地。  
- **技术实现**：关键高危点已经用硬约束锁死（异步 AI、Redis 原子锁、不可提现、一级推荐等）。  
- **合规**：v3.0 把分账切掉后，资金流反而更干净，老带新用抵扣券，性质是「消费奖励券」，不是资金分配或预付卡。

所以：**闭环现在是可落地的，没有原则性大坑**，但有几个需要「打磨」的地方。

### 1.2 闭环还需完善的关键点

**1）商家停用后的「善后体验」**（数据导出 + 顾客权益）

现状：  
- 协议里有「30天内可导出、90天后删除」，但没细化「导出什么、格式如何、怎么点」。
你要补足：  
- 后台一个「一键打包导出」按钮，一次导出 5 个 Sheet：  
  - 会员列表（手机号脱敏，含等级、累计消费）  
  - 消费记录  
  - 推荐关系（谁带来的谁）  
  - 余额明细  
  - 抵扣券明细  
- 导出后给商家一个 7 天有效的下载链接，同时在协议里明确「导出=商家已取得数据副本」，30 天后主库删、90 天后归档库删。

意义：  
- 商家放心「随时可以带走数据」，愿意先试。  
- 真停用时口碑不会崩——**你不给「人走数据在」的恐惧感**。

---

**2）抵扣券的到期提醒和文案**（影响核销率、商家真实感受）

系统侧你已经有：  
- 14/7/3/1 天的到期提醒任务。  
还要补的是「**文案 + 策略**」，否则商家只看到你报一个 40% 或 60% 的核销率数字，没感觉你是在帮他「控成本」。

建议：  
- 默认策略（可在后台说明里写）：  
  - 有效期：30 天  
  - 14 天：轻提醒（「你有一张 10 元券即将到期，来店消费可用」）  
  - 7 天：中度提醒  
  - 3 天 + 1 天：强提醒（带轻微「最后机会」感）  
- 跟老板算账时直接讲「**你发了 100 张券，我们会帮你至少提醒 4 次，目标是核销率 50%-60%，而不是 100%」——他会意识到你在帮他「控制支出」而不是「放水」。

---

**3）异常核销 & 刷单防控的落地 SOP**

规则层面你已经有 14 条风控规则，但运营侧没有写清「发现异常后怎么办」，建议：

- 按严重程度分级：
  - **P0**：单日某员工核销金额 > 店月均营业额的 20%；  
  - **P1**：单日同一个顾客核销 3 次以上；  
  - **P2**：AI 用量异常（某店一个小时几百次生成）；  
- 每天早 10 点运营合伙人打开「告警列表」，先处理 P0，再 P1。  
- 每次处理必须写「备忘」：原因判断 + 处理动作（冻结/放行/拉黑）。

这样你对老板可以说一句很有安全感的话：  
> 「系统每天会自动帮你盯异常单子，有问题我们先给你打电话，不会让你‘亏了还不知道’。」

---

**4）试点期「成功 / 失败」的沟通模板**

你协议里已经有：「扫码率≥30%、老带新≥10 单、余额核销率≥40%，任意两项达标算成功」。  
缺的是——28 天到了，你怎么跟老板「讲结果」。

建议在 PRD 外再写一页「试点期体检报告模板」，固定 4 块内容：  

1. 数据：三项指标 + 你帮他算的增量营业额（下面我给你一套详细账）。  
2. 亮点：哪一块超出预期（比如某天因门店搞活动，晒圈暴涨）。  
3. 问题：比如某些时段没有扫码，说明员工提示不足。  
4. 决策：签正式合同 / 延长 14 天再试 / 调整策略后再观察。

- **不要只看注册人数**：所有决策看三件事：扫码率、老带新单量、核销率（余额+券）。  
- **首月绝对不谈「扩店」**：前 1–3 家店只要打爆数据，不要忙着签第 10 家。你的护城河来自「数据 + 续费」，不是「签约数量」。

  - **商家成本占比**  
再决定是否默认打开「梯度激励」。

3）**更细的数据报表给商家**  
第一版就一个周报；2–3 个月后可以加：  
- 「高价值顾客 Top 50」——刷脸的是：总消费额 + 老带新次数；

## 三、给商家算账：更「有感觉」的一版

你跟老板聊的时候，不能只扔数字，要让他「在自己店里」感觉到。

### 3.1 从他熟悉的「一天」开始算

以一个**30 桌火锅店，人均 80 元**为例。  
假设老板说「我们店差不多一天三四十桌」。

你可以这样引导：

> 「那我们先按 **一天 40 桌** 算，一桌 3 人，就 **120 个人/天**。  
> 一个月按 25 天算，就是 **3,000 人** 真正坐在你店里吃过饭。」

现在他脑子里有画面了——每天客流、月客流。

### 3.2 把每一步都连回「你每天店里」

**1）有多少人会扫码？**

行业上微信私域类小程序的扫码/激活转化率一般是 30%-50%[7]，结合火锅场景（等菜时间长、年轻人多），你可以这样说：

> 「保守按 **40% 扫码率** 算，就是一天 120 个人里有 48 个会扫码，一个月就是 **1,200 个顾客扫码进入你的小程序**。」

**2）这 1,200 个里，有多少人会玩 AI 晒圈？**

晒圈是更高阶的行为，不是人人都干。你可以参考社交裂变活动里老带新参与率数据（老带新活动一般 20%-30% 的人愿意参与）[8]：

> 「我们不按网红店算，按普通店，**25% 的扫码顾客会玩晒圈**，就是每个月大概有 **300 个人用你店里的 AI 做朋友圈海报**。  
> 这 300 个人不是你找的，是系统帮你把他们激活的。」

**3）300 个人晒圈，会带来多少新客？**

老带新场景下，用研究里的数据：通过熟人推荐过来的用户首单转化率可以到 60% 以上[8]，但每个人不会都带一个人来，我们保守：  
- 300 人里，有一半认真发了  
- 每个认真发的人里，有 40% 至少带来 1 个新客  

你对老板的说法可以简化成：

> 「我们简单粗暴地算：  
> **300 个人发圈，每 4 个人里有 1 个人能实实在在带来一个朋友来吃**。  
> 也就是说一个月大概是 **75 个新客**（300 ÷ 4）。」

**4）75 个新客，对生意意味着什么？**

- 新客人均消费：80 元  
- 新客营业额：75 × 80 = **6,000 元**

你可以接着问一句：「**你现在在美团上花 6,000 元，能不能稳稳给你多 75 个新客？**」  
（平台上单次新客成本通常 30–80 元，这句话他心里有数）

**5）这 75 个里，有多少会变成「常来的人」？**

现实中：  
- 线下自然复购率（没做任何私域）20%-30%[4][6]；  
- 进私域、经常被触达的会员的复购率可以显著提升，很多研究都在「复购率每提升 3 个点，净利可以提升 12%-18%」[6] 这个区间。

你可以给老板一个「非常生活化」的说法：

> 「有的客人跟你加了微信、进了你的小程序，他后来再吃火锅时，大概率会先想到你。  
> 我们不算夸张的，只算 **多回来 10%**。  
> 75 个新客里，多 10% 回来，就是 **7–8 个人再来吃一顿**。  
> 一顿还是 80 元，那又是 **600 元左右**。」

**6）老客复购 + 原有顾客复购一起算**

别忘了，系统不仅影响「新客变熟客」，也会影响原有老客的复购率。  
你可以直接拿行业的那句：

> 「QuestMobile 有个 2026 白皮书，说的是：**会员复购率每提升 3 个百分点，门店净利润可以增长 12%-18%**[6]。  
> 我们不算 12%，就按 **10% 净利润增长** 来看。」

假设这家店本身月净利润 2 万：  
- 净利润提升 10% = 2,000 元多赚净利润  

配上前面的新客+复购算式，整套账就可以讲成「两层」：

1. **看营收**：  
   - 新客吃一顿：6,000 元  
   - 其中一部分回来再吃一顿：600–800 元  
   **增量营业额 ≈ 6,600–6,800 元/月**

2. **看利润**：  
   - 原本月净利润 2 万，复购率多 3–5 个点，**净利至少多 2,000 元**[6]。  
   - 减去你的成本（后面算）之后，**系统本身带来的净利增量是正向的**。

你最后可以给老板一句总结：

> 「你现在每个月在美团/抖音花出去的那点钱，只能带来一次性的新客；  
> 我们是让每个月这 3,000 个已经坐在你店里的人，帮你多带来一批人，并且这一批人里有一部分会留下来做你的‘自己的顾客’。」

这时候数字只是辅助，他脑子里已经有了画面：有人扫、有人晒、朋友圈有人来吃。

## 五、独立 App 的规划：什么时候值得做、要考虑什么

### 5.1 什么时候值得从小程序升级为独立 App？

**不建议早做 App。** 主要原因：

- 餐饮现场场景下，**微信小程序扫码体验是最自然的**，顾客不会为一个门店专门下 App。  
- 你的核心在于「SaaS + 裂变玩法」，不是搞一个 C 端流量 App。  

更合理的路线：

1. **0–100 家店：只做微信小程序（用户端+商家端）**  
   - 把微信生态吃透：扫码、服务通知、企微私域等。  

2. **100–500 家店：评估多端统一的必要性**  
   - 比如有商家希望在 PC 上看报表、有品牌要在安卓手持机上用商家端等。  
   - 这时可以上：  
     - PC Web 管理后台  
     - 安卓「商家版 App」（给店员/店长用）  

3. **500 家店以后再考虑 C 端 App**，前提是：  
   - 你掌握了足够多的「跨店数据」；  
   - 你希望做「面向消费者的品牌」（比如「燎客美食」）——把用户账号和权益跨店打通。

### 5.2 一旦做独立 App，要考虑的关键点

1）**账户打通与多端登录**

- 现在用户 ID 是基于微信 openid 的；  
- 做 App 时必须有一个「自有账号体系」（手机号+验证码登录）；  
- 需要一套「账号合并逻辑」：  
  - 同一个手机号在微信和 App 上登录，要映射到同一个 user_id；  
  - 推荐关系、余额、抵扣券要按 user_id 维度统一。

2）**推送体系的迁移**

- 小程序时代所有触达靠「服务通知」；  
- App 时代要用各家推送通道（小米、华为、OPPO、APNs）；  
- 你需要一个「用户消息中心」：  
  - 同一条消息，在小程序、App、公众号三个入口尽量不重复骚扰；  
  - 让用户可在 App 里设置「只要哪一种推送」。

3）**合规重新评估**

- 一旦做独立 App，你就不再完全「藏」在微信生态里：  
  - 可能要单独过一遍 **隐私合规评估**（特别是你涉及用户行为数据、位置数据等）；  
  - App 商店（尤其是苹果）对「抽成、虚拟支付」有独立规则，你要避免用 IAP 收 SaaS 订阅费。

4）**团队能力要求**

- App 意味着同时维护：  
  - iOS 客户端  
  - 安卓客户端  
  - 微信小程序（用户端+商家端）  
  - 后端、运营后台  

以你现在的资源，不适合在 0–2 年内同时撑起这么多端。更合理：  
- 第一步：小程序用户端 + 小程序商家端 + Web 后台  
- 第二步：安卓商家 App（如果很多店员不用微信）  
- 第三步：C 端 App（真有大量跨店玩法时）

## 一、整体定位：积分在你系统里的角色

你现在已经有三套“值”：

- 成长值：只升不降，用来判断等级（Lv1–Lv4），和折扣权益挂钩；
- 余额（cashback）：按消费金额返现，下次消费抵扣现金；
- 老带新抵扣券：朋友来吃，给老客一张下次抵扣的现金券。

现在新增：

> **积分 = 纯礼品/服务兑换的“代币”，不和现金直接挂钩，只能兑换小菜/饮料/小吃/服务。**

原则：

1. **和钱完全隔离**：不可抵扣金额、不可提现、不可折价；  
2. **和成长值分工明确**：成长值→等级；积分→换实物/服务；  
3. **默认门店单独配置**：每家店自己决定送什么、多少分换；  
4. **体验要简单**：顾客页面就两层：  
   - “我现在有多少分”  
   - “这些分能换什么好玩的东西”。

|------|------|----------|

| 每日到店签到一次 | 5积分 | 增加非消费触达，拉回到店频次 |

- **只能用于兑换“赠品/服务”**，不抵现金，不参与订单金额计算；
- 支持两种商品类型：
  - 实物：凉菜一份、小吃一份、饮料一杯、纸巾一包等；

兑换逻辑：

- 下次到店，顾客出示兑换码 → 店员在商家端点「积分兑换核销」扫码 → 赠品给到顾客。

## 五、积分对商家「账本」的影响（你怎么讲）

你要让老板感觉：

> 「积分是‘小恩小惠’，并不会压垮利润。」

### 5.1 粗略成本模型（给老板讲得懂）

继续用前面的 30 桌、人均 80 的店：

- 消费获得积分：10 分/元  
  - 一次 80 元消费，得 800 积分  
  - 顾客平均来店 3 次，就有 2400 分  

你设计几个兑换档位：

- 500 分 → 一杯酸梅汤（成本约 3 元）  
- 800 分 → 一份凉菜（成本约 4 元）  
- 2000 分 → 一次优先排队服务（几乎没成本）

跟老板讲一个「感觉」：

> 「你可以把积分理解成：**每消费 80 元，我给你返‘3–5 元的货’，还是以‘小礼品’的形式给回去**，  
> 顾客的心理感受是‘赚到了’，你的真实成本比直接打折要低很多。」

如果你希望严谨一点，可以：

- 预计 20% 的积分最终会被兑换（很多人会忘记、会懒得用）；
- 发出去的积分面值 100%，实际成本可能是 50%（只换成本较低的饮料/小菜）。

你对老板的最终话术：

> 「我们会帮你把这个积分的设计，控制在**整体毛利里出个 2–3 个点**，但能明显提高顾客的好感和回来次数。」

## 六、和现有体系的关系 & 风险点提醒

1. **不要用积分抵扣金额**：  
   - 一旦「积分 = 钱」，就很容易踩到预付卡 / 金融合规红线；  
   - 你现在已经有「余额」做钱，积分只做实物/服务兑换，最安全。

2. **积分规则尽量简单**：  
   - MVP 阶段少搞复杂的“连续签到 7 天翻倍”、“等级系数”等；  
   - 先用固定规则验证顾客是否买账，再做高级玩法。

3. **商家后台默认给一套模板**：  
   - 很多老板不想自己算积分，应提供：  
     - 「保守版」（成本更低）  
     - 「激进版」（多送点礼但效果更好）  
   - 你可以在运营手册里写出这两套方案，跟老板勾选。

# 二、数据结构：新表 + 原表补字段

## 2.1 新增表一览

| 表名 | 用途 |
|------|------|
| `points_accounts` | 每个用户在每个门店的一条积分账户记录 |
| `points_transactions` | 所有积分收入/支出流水 |
| `points_products` | 积分可兑换的商品或服务（按门店配置） |
| `points_redemptions` | 每一笔积分兑换记录（含兑换码、核销状态） |

### 2.1.1 `points_accounts`（积分账户表）

- 一人一店唯一一条，用于快速展示当前剩余积分

字段核心：

- `user_id` / `store_id` / `total_points` / `total_earned` / `total_used`  
- `expire_at`：门店配置整体有效期时，可使用此字段做“总清零”；若做成按笔有效期，则以流水表为准，这个可以先留白。

约束：

```sql
UNIQUE INDEX uk_user_store (user_id, store_id);
```

### 2.1.2 `points_transactions`（积分流水表）

每一笔积分变化（+/-）都写一条记录，支持按来源统计、按时间查询。

关键字段：

- `tx_type`：`consume_earn` / `sign_in` / `ai_share` / `profile_complete` / `birthday` / `redemption` / `expired`
- `points_amount`：正数=获得，负数=消耗
- `points_before` / `points_after`
- `order_id`：消费获得积分时填原订单ID
- `redemption_id`：兑换时填写

如果你希望以后支持“积分按笔有效期”（例如新积分有效一年，老积分先过期），可以在这里加 `expire_at` 字段，一开始可以先不严格用到，逻辑上预留出口。

### 2.1.3 `points_products`（积分商品配置）

按门店配置，字段要满足：

- 商品基本信息：`product_name` / `product_type` / `image_url`
- 成本控制维度：
  - `points_required`（所需积分）
  - `stock_quantity`（库存，不限就9999）
  - `monthly_limit_per_user`（每人每月限兑次数）
- 上下架：`is_active` / `sort_order`

店内典型默认模板（你在运营手册里给商家一套推荐值）：

| 商品 | 建议积分 | 解释 |
|------|----------|------|
| 酸梅汤一杯 | 500 分 | 消费两次左右就能换一次饮料，制造“够得着”的感觉 |
| 凉菜一份 | 800 分 | 约相当于消费 1 次人均 80 元 |
| 小吃一份 | 1000 分 | 稍高一点，鼓励多来几次 |
| 优先排队一次 | 2000 分 | 高价值服务，几乎零成本 |
| 包厢费减免一次 | 3000–5000 分 | 适合有包厢的店，高感知价值 |

### 2.1.4 `points_redemptions`（积分兑换记录）

- 一笔兑换对应一条记录：谁、在哪家店、换了啥、扣了多少分、兑换码、状态。

关键字段：

- `redeem_code`：8 位短码（和优惠券码格式类似），唯一索引；
- `status`：`active` / `used` / `expired` / `cancelled`
- `expire_at`：默认兑换后30天；
- `verifier_id` / `used_at` / `used_order_id`：商家端核销时填入。

约束：

```sql
UNIQUE INDEX uk_redeem_code (redeem_code);
INDEX idx_user_store_status (user_id, store_id, status);
INDEX idx_expire_at (expire_at);
```

# 三、核心业务逻辑设计

## 3.1 积分获取逻辑

### 3.1.1 消费获得积分

在「核销回调」逻辑里增加一步：

```python
def handle_verify_callback(...):
    ...
    # 原有：返现逻辑、成长值逻辑、等级升级逻辑
    ...
    # 新增：消费获得积分
    if store.points_enabled:
        points = int(order_amount) * store.points_per_yuan  # 80元=>800分
        add_points(user_id, store_id, points, tx_type='consume_earn', order_id=order_id)
```

`add_points` 的关键点：

- 读当前 `points_accounts.total_points`；
- 计算 `points_before`/`points_after`；
- 写 `points_transactions`；
- 更新 `points_accounts`（带乐观锁或简单 UPDATE）。

### 3.1.2 签到、AI晒圈、完善资料、生日

这些不用每单都进事务，可以：

- 在对应行为接口里，判断今天有没有给过：
  - 签到：Redis `sign_in:{user_id}:{store_id}:{date}`；
  - AI晒圈：同一个晒圈行为成功后，发一次积分；
  - 完善资料：只发一次，`user_profile_completed` 标志；
  - 生日：校验用户生日在当月，且当月还没发。

例如「每日签到」逻辑：

```python
def daily_sign_in(user_id, store_id):
    if not store.points_enabled:
        return
    key = f"points_sign:{user_id}:{store_id}:{today}"
    if redis.SET(key, "1", NX=True, PX=24*3600*1000):
        add_points(user_id, store_id, store.points_sign_in_daily, 'sign_in')
    else:
        # 今日已签到，不重复加分
        pass
```

## 3.2 积分兑换逻辑（用户端）

### 3.2.1 展示可兑换商品列表

接口示意：`GET /api/user/points/products?store_id=xxx`

返回内容：

- 当前积分 `current_points`
- 商品列表（只返回 `is_active=1` 且 `stock_quantity>0` 的）

前端根据 `current_points >= points_required` 决定按钮可点/置灰。

### 3.2.2 发起兑换

接口：`POST /api/user/points/redeem`

请求：

```json
{
  "store_id": "S001",
  "product_id": "P001"
}
```

后端逻辑（事务）：

1. 读商品，检查 `is_active=1` 且 `stock_quantity>0`；
2. 检查「每人每月限兑」：  
   - 查 `points_redemptions` 表：`WHERE user_id=? AND product_id=? AND MONTH(created_at)=当月 AND status IN ('active','used')` 数量 < `monthly_limit_per_user`；
3. 检查用户当前积分是否够；
4. 扣积分：写 `points_transactions`（负数），更新 `points_accounts`；
5. 减库存：`stock_quantity-1`（如无限库存可不减）；
6. 生成 `redeem_code` + `qr_code_url`，写 `points_redemptions` 记录（status=active，expire_at=NOW+30天）；
7. 返回兑换码信息给前端。

注意：事务里要设好整数溢出保护和库存 >=0 判断，防止一秒内多次请求导致库存负数。

## 三、积分模块（v3.1）的定位与价值

你现在的设计优点在于：
